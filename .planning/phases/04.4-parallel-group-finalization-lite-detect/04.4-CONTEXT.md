# Phase 04.4: Parallel Group Finalization & Lite Detect Swap - Context

**Gathered:** 2026-06-02
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 4.4 is a corrective follow-on to Phase 4.3. The deterministic clarification UI stays in place, but the current save path is too lossy when it turns structured clarification answers straight into `confirmation_items` and persists those fragments as final food records. In the live `sample_images/IMG_4646.HEIC` run on 2026-06-02, the meal completed, but the saved `FoodItem` names became `Bran and whole wheat`, `Green masala`, and `Lauki`, and the captured bread quantity did not persist into the final `DiaryEntry` rows.

This phase inserts a compact post-clarification finalization step before the authoritative write transaction. Instead of asking the user anything new, the system should run one structured LLM call per food group, in parallel, using `google/gemini-3.1-flash-lite`. Each call should consume only that food group's reasoning result plus that group's clarification answers and produce save-ready metadata for the existing final write path.

This phase also swaps the detect/classification model from `google/gemma-4-31b-it` to `google/gemini-3.1-flash-lite` so the low-cost Lite model is used both at the front of the pipeline and in the new per-group post-processing layer.

</domain>

<decisions>
## Implementation Decisions

### Per-Group Post-Processing Shape
- **D-01:** Run post-processing at the food-group level, not the whole-meal level. One finalized metadata payload should be produced per grouped food item.
- **D-02:** Fan out per-group finalizer calls in parallel with bounded concurrency. This is an orchestration step, not a serial loop over all groups.
- **D-03:** Each finalizer call must be scoped to one group's own context: grouped reasoning outcome, `top_3`, `group_actions`, selected clarifications, `segment_ids`, and any relevant crop refs or confirmation payload.
- **D-04:** The per-group finalizer must not ask new user-facing questions. It is a metadata composer only.
- **D-05:** The per-group finalizer output must be strict structured JSON and fail closed if malformed.

### Save-Ready Metadata Contract
- **D-06:** The finalizer output should be save-ready metadata for the existing authoritative transaction, not a replacement write path.
- **D-07:** At minimum, the finalizer output must include a proper final dish name, source type when known, quantity payload/display when known, portion bucket, and fields needed to create or update the learned FoodItem/FoodVisual record.
- **D-08:** Clarification answers that materially affect persistence must survive finalization. Bread count, source/origin, corrected identity, and user-provided free-text detail cannot be dropped.
- **D-09:** Final names should preserve food identity, not just answer fragments. A style answer like `Green masala` must not become the whole saved food name when the grouped food is clearly a chicken curry.
- **D-10:** The finalizer may emit alias/supporting metadata alongside the final name when that helps the learning loop, but the saved primary name must remain a dish-level identifier.

### Write Path Ownership
- **D-11:** `apply_final_meal_resolution()` remains the authoritative write path. Phase 4.4 should improve inputs to that transaction, not fork a second save system.
- **D-12:** Existing grouped clarification state in `MealLog.reasoning_state_json`, `InterviewSession.current_prompt_payload`, and durable answer payloads remains the source material for finalization.
- **D-13:** The finalizer should attach metadata needed to accompany visual learning before save, so the resulting FoodVisual/DiaryEntry pair reflects the clarified outcome instead of the pre-finalized fragment.
- **D-14:** If one group finalizer fails, the planner may choose a bounded retry and a per-group degraded fallback, but the failure policy must be explicit and testable. Silent lossy fallback is not acceptable.

### Model Decisions
- **D-15:** Use `google/gemini-3.1-flash-lite` for the new per-group post-processing/finalizer calls.
- **D-16:** Swap the detect/classification model default from `google/gemma-4-31b-it` to `google/gemini-3.1-flash-lite`.
- **D-17:** Keep the existing detect-stage structured contract and conservative fail-closed behavior; Phase 4.4 changes the model default, not the external detect interface.

### Scope Fence
- **D-18:** This is not Phase 5 grounding. Do not add SearXNG or Firecrawl calls, URL fetch loops, brand/restaurant nutrition search, or general web grounding.
- **D-19:** This is not a new freeform interview phase. The user-facing clarification UI stays deterministic as delivered in Phase 4.3.
- **D-20:** This phase exists to repair final metadata quality and preserve clarification answers before save, while keeping the Phase 4 authoritative transaction intact.

### the agent's Discretion
- The planner may choose the exact structured schema for per-group finalizer output as long as it is strict, compact, and sufficient for the existing save path.
- The planner may choose where bounded parallelism lives for the finalizer fan-out, as long as it reuses the current worker ownership boundaries and does not create a second background subsystem.
- The planner may decide whether quantity is represented as normalized JSON, a display string, or both internally, provided the persisted save path no longer drops user-supplied quantity answers.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `reasoning_state_json` already persists grouped reasoning, `answers_by_question_id`, `confirmation_items`, and resolver payloads; Phase 4.4 should reuse these state surfaces rather than inventing a new store.
- `interview_service.finalize_confirmed_interview()` is the current pivot point where clarified groups become final save inputs; this is the obvious seam for per-group post-processing.
- `meal_resolution_service.apply_final_meal_resolution()` already owns authoritative database writes and should stay unchanged as the final transaction boundary.
- `bot/polling.py` already contains bounded worker orchestration patterns and a post-interview worker path that can inform the new parallel group finalizer fan-out.
- `vision_service.detect_food_photo()` already has a strict classification contract and tests that can absorb the detect-model swap with minimal surface churn.

### Observed Failure That Motivates The Phase
- Live meal `1ff2a93e-87d3-4214-bb5b-a8e8042034c5` completed after deterministic clarification, but the saved FoodItems became `Bran and whole wheat`, `Green masala`, and `Lauki`.
- The meal state correctly captured the user's `2 pieces` bread answer, but final `DiaryEntry.quantity_display` and `DiaryEntry.quantity_json` remained null.
- The final meal state shows `completed_by: interview_service`, which means the authoritative save was fed directly from grouped clarification outputs instead of a richer per-group final metadata pass.

### Integration Points
- Insert per-group structured finalizer calls between clarification completion and `apply_final_meal_resolution()`.
- Feed each call one group's reasoning block plus that group's answer payloads and segment refs.
- Persist the returned metadata into the existing final-resolution objects so FoodItem, DiaryEntry, and FoodVisual rows reflect the clarified dish identity.
- Update config/tests for the `DETECT_MODEL` default swap to `google/gemini-3.1-flash-lite`.

</code_context>

<specifics>
## Specific Ideas

- Treat the per-group finalizer as a "last mile metadata composer" rather than a second reasoning system.
- For the `IMG_4646.HEIC` case, the expected improvement is that answers like `Bran and whole wheat`, `Green masala`, and `Lauki` become fuller grouped food records before persistence, rather than raw fragments saved as primary item names.
- The finalizer should be able to combine group label plus clarification answers into a better canonical save record, for example a clarified bread type, a chicken curry style, or an egg-and-vegetable curry identity, without requiring any new user interaction.
- Quantity and source/origin should be carried through the same finalizer output so the authoritative save path can persist them consistently.

</specifics>

## Deferred Ideas

- Broader model rationalization across all stages beyond detect + per-group finalizer remains out of scope for this phase.

</deferred>
