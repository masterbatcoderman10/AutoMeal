# Phase 4.5: Source-Aware Clarification Expansion - Context

**Gathered:** 2026-06-02
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 4.5 extends the deterministic Telegram clarification flow before the existing Phase 4.4 per-group LLM finalizer runs. It adds source-aware questioning for groups with weak or ambiguous learned evidence, adds learned-source affirmation when historical source patterns are strong enough, preserves the current partial-answer and durable-state behavior, and keeps the finalizer as a downstream metadata composer rather than turning it back into a user-facing interview engine.

</domain>

<decisions>
## Implementation Decisions

### Source Trigger Rules
- **D-01:** If a food group has no vector match or fewer than 5 vector matches, the deterministic clarification flow must ask the source question even if the reasoning output did not explicitly request one.
- **D-02:** Identity comes before source in the ambiguous learned-distribution path. The system should first resolve what the food is, then decide whether a source prompt is still needed for that chosen identity.
- **D-03:** Existing clarification ordering, answer storage, partial-reply recovery, and question rerender behavior must remain intact. Phase 4.5 adds questions to the current deterministic engine; it does not replace the flow.

### Retail Source Semantics
- **D-04:** Keep `PACKAGED_BRANDED` distinct from `STORE_BOUGHT_PREPARED`. Example guidance from the user: khubz from a brand like Al Khayam is packaged/branded, while ID parottas are store-bought prepared.
- **D-05:** The store-bought retail branch still asks for brand when helpful, and the restaurant branch asks for restaurant name. These follow-ups remain free-text answers stored in the deterministic interview state.
- **D-06:** Source questioning is still pre-finalizer input gathering. The resulting source, brand, and restaurant answers are passed forward to Phase 4.4 finalization rather than resolved in a separate interview subsystem.

### Learned Source Distribution Behavior
- **D-07:** If a food group has 5 or more high-score learned matches but the identity distribution is still not definitive, the user should still be asked to choose the identity.
- **D-08:** After the identity is chosen, if the learned history for that selected identity shows a clear dominant source, do not ask the generic source question. Instead, ask an affirmation such as: "Most of `<item>` readings so far have been `<source>`, agreed?"
- **D-09:** If the chosen identity does not have a compatible learned source distribution, or the learned source pattern is not dominant enough to support affirmation, fall back to the generic source question.
- **D-10:** The exact dominance threshold and distribution-calculation heuristic are planner discretion, but the user intent is clear: use learned source consensus only when it is meaningfully stronger than a generic source question.

### Failed Affirmation Behavior
- **D-11:** When an affirmation is answered with `No`, the next prompt should be a free-text correction request rather than another forced-choice ladder.
- **D-12:** That free-text correction is accepted as the user answer to pass into downstream post-processing/finalization, preserving the same group and `segment_ids` context as the rejected affirmation.
- **D-13:** This failed-affirmation correction path should apply to the new learned-source affirmations as well as existing identity affirmations.

### Group Contract And Integration
- **D-14:** The grouped reasoning contract must expose a stable `segment_ids: string[]` field per food group in the model-facing reasoning/output schema. Downstream logic should not need to reconstruct group membership from `segment_indexes` alone.
- **D-15:** Phase 4.5 is an interview/Telegram extension phase. It must not alter the role of the Phase 4.4 per-group finalizer, introduce grounding calls, or reopen whole-meal LLM interviewing.

### the agent's Discretion
- The planner may choose the exact learned-source dominance threshold, as long as it only triggers source affirmation when the historical pattern is genuinely strong.
- The planner may choose whether the source-affirmation prompt is rendered as a confirm button pair or an equivalent deterministic confirmation interaction, as long as rejecting it leads to a free-text correction path.
- The planner may decide whether retail brand follow-up is injected immediately after the source answer or through the same dynamic question insertion mechanism already used for clarification follow-ups, provided the durable state contract stays unchanged.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `reasoning_service._build_source_origin_action()` and related clarification-action helpers already synthesize deterministic source questions and can be extended for the new trigger rules.
- `interview_service._clarification_questions_from_food_groups()` and `_build_clarification_question_state()` already preserve ordered deterministic question state keyed by stable `question_id`.
- `interview_service._apply_clarification_answer()` already supports dynamic follow-up question insertion while preserving `pending_question_ids`, `remaining_required_question_ids`, and durable answer state.
- `interview_service._build_affirmation_correction_question()` already converts a rejected affirmation into a required free-text correction question; 4.5 can reuse this behavior for learned-source affirmations.
- Phase 4.4 finalizer inputs already carry `segment_ids`, group-scoped clarification answers, and group-specific finalization payloads, so 4.5 can enrich answers without changing the finalizer seam.
- `bot/callback_data.py` and the existing `Other` flow already support deterministic button-based choices with a free-text escape hatch.

### Established Patterns
- Deterministic clarification state is durable and group-scoped. New 4.5 source/brand/restaurant prompts should live in the same `questions_by_id` and `answers_by_question_id` surfaces rather than inventing parallel state.
- Source-origin answers currently normalize into `HOME`, `PACKAGED`, and `RESTAURANT` output types while still preserving finer `source_origin_state` detail.
- Clarification questions are additive and ordered. Existing required questions rerender until satisfied, and only unanswered required questions are re-prompted.
- The current code already treats a rejected affirmation as a free-text correction path. The new learned-source affirmation should follow that exact pattern instead of adding a new exception flow.

### Integration Points
- Extend the model-facing reasoning schema in `app/services/reasoning_schema.py` so food groups explicitly emit `segment_ids`.
- Extend `app/services/reasoning_service.py` to synthesize source questioning from vector-match count and learned-distribution state, not only from model-authored `ASK_SOURCE_ORIGIN` hints.
- Add learned-source consensus metadata at the group or candidate level so the interview layer can render "most readings so far..." affirmations after identity selection.
- Extend `app/services/interview_service.py` so choosing store-bought/packaged or restaurant injects the correct free-text follow-up question while preserving the current deterministic state machine.
- Ensure the enriched answers continue to feed the Phase 4.4 per-group finalizer through the existing group-scoped clarification answer payloads.

</code_context>

<specifics>
## Specific Ideas

- Branded khubz such as Al Khayam should be treated as packaged/branded retail food, while products like ID parottas should remain store-bought prepared.
- For foods like rice with many strong historical readings, the user wants a source-consensus affirmation such as "Most of rice readings so far have been home, agreed?" instead of a generic source question when the source pattern is clearly dominant.
- When an affirmation is rejected, the next question should be a free-text correction that passes directly into post-processing/finalization rather than forcing another choice list.
- The phase must remain explicitly pre-finalizer. It enriches deterministic answers; it does not move decision ownership away from the existing Phase 4.4 finalizer.

</specifics>

<deferred>
## Deferred Ideas

- Phase 5 still owns grounding, SearXNG/Firecrawl lookup, and any source-to-nutrition fetch behavior.
- Broader changes to the Phase 4.4 finalizer contract remain out of scope; this phase only enriches the deterministic clarification inputs it receives.
- Any larger learned-distribution UX beyond source consensus, such as richer historical-brand suggestion UIs, can be evaluated after the 4.5 source branch is working.

</deferred>
