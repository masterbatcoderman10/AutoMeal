### GAP-04.3-P1: Optional Approval Correction Path Is Not Deterministic Enough

Evidence:

- The active state reached `pending_question_ids=["chicken_curry_group:confirm"]` with `remaining_required_question_ids=[]`.
- The bot sent:

```text
I couldn't safely apply that answer yet. Please answer the same meal question again:
I likely have Chicken Curry with Drumstick. Is that right?
```

- `last_turn_error` showed:

```text
ready_to_confirm approved group chicken_curry_group without explicit user confirmation
ready_to_confirm corrected group chicken_curry_group without explicit user evidence
```

Root issue:

- Optional approval prompts (`Yes`/`No`) are being mixed with the resolver confirmation path.
- A `No` answer does not become a deterministic follow-up asking for the corrected food name for that group.
- A typed correction after `No` is treated as a broad confirmation edit, so the validator can still reject it as insufficient explicit evidence.

Acceptance criteria:

- If the user taps `No` on an approval prompt, the next prompt must be a deterministic free-text correction for that same group.
- The typed correction must be stored as the explicit evidence for that group and must not call the LLM resolver just to prove the correction exists.
- After the correction, the flow should proceed to final confirmation/write without re-asking the same Yes/No question.
- Add contract tests covering `No -> typed correction -> final confirmation` for deterministic meal interviews.

### GAP-04.3-P2: Grounding Handoff Blocks Final Writes Too Aggressively

Evidence:

- After correction, the bot reported:

```text
Thanks. Meal d883c4a4 still needs packaged or restaurant grounding, so I've queued the next step and won't write final entries until it completes.
```

- Bot logs show OpenRouter quota failure during grounding:

```text
Error code: 403 - Key limit exceeded (total limit)
```

- Current session state is `GROUNDING_PENDING` / `RETRY_PENDING`, with no final diary entries written.

Root issue:

- Selecting `PACKAGED_BRANDED` or `RESTAURANT` turns grounding into a hard blocking state for final diary writes.
- Provider quota/external failure is presented as normal queued progress rather than an actionable blocker.
- The system lacks a degraded path such as logging the user-confirmed identity with `NEEDS_GROUNDING` nutrition status.

Acceptance criteria:

- If grounding cannot complete because of provider quota/network/tool failure, the bot must say the concrete blocker and not imply normal queue progress.
- User-confirmed meal identity should be written or explicitly held according to a clear policy, not silently stranded in an active interview.
- Add a retry/degraded-state contract test for post-interview grounding failure.
