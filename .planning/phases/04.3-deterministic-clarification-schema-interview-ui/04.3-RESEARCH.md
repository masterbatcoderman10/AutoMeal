## User Constraints (from CONTEXT.md)

### Locked Decisions

### Reasoning Output Contract
- **D-01:** `food_groups[*].top_3` is the active source of truth for candidate rankings. The current root-level `top_3` should be removed from active reasoning semantics or kept only as a short-lived compatibility adapter during migration.
- **D-02:** Meal reasoning must emit a strict `clarification_schema` alongside `food_groups` when any food group needs user input or approval.
- **D-03:** `clarification_schema` questions must have stable IDs, group IDs, primary segment ID, segment IDs, question kind, answer type, required/optional status, choices when applicable, and validation hints.
- **D-04:** Valid answer types for this phase are `single_choice`, `multi_choice`, `free_text`, and `confirm`. The planner may add internal enum names, but the user-facing behavior must stay this small.
- **D-05:** Question schema should be compact and cache-friendly. Do not push long prose instructions into every question; templates render the prose.

### Deterministic Telegram Clarification UI
- **D-06:** Telegram questions are rendered deterministically from templates, not composed by an interview LLM.
- **D-07:** MCQ/confirm questions should prefer Telegram buttons or reply markup where the existing bot architecture supports it; free text remains available for open-field corrections and "other" answers.
- **D-08:** Every user answer must map back to a stable question ID and be stored durably in `InterviewSession.current_prompt_payload` and/or `InterviewMessage` payloads.
- **D-09:** Partial replies are first-class. If the user answers only some required questions, the system must deterministically re-prompt only the remaining required questions and preserve prior answers.
- **D-10:** The bot must not loop on approval candidates that were already answered in prior structured state.

### Conditional Source-Origin Clarification
- **D-11:** Add source-origin clarification only when it can materially change nutrition or grounding behavior. Examples: flatbreads, packaged-looking foods, bakery items, sauces, takeout, desserts, branded/label-visible foods, or restaurant-looking items.
- **D-12:** Do not ask homemade/store-bought/source-origin for obvious home-cooked foods such as a clearly home-style curry unless visual evidence or candidate context indicates ambiguity.
- **D-13:** Source-origin options should distinguish at least `HOME_COOKED`, `STORE_BOUGHT_PREPARED`, `PACKAGED_BRANDED`, `RESTAURANT`, and `UNKNOWN`, but the user-facing copy can say "homemade", "store bought", "packaged", "restaurant", and "not sure".

### Final Resolver Skeleton
- **D-14:** Reuse the current interview LLM only as a toned-down final resolver skeleton after deterministic answers are collected.
- **D-15:** The resolver must not ask user-facing interview questions. It receives compact grouped reasoning, structured answers, and prior confirmations, then emits strict `confirmation_items`.
- **D-16:** The existing final write path remains authoritative. The resolver output must flow through the same transaction that creates or updates FoodItems, DiaryEntries, and FoodVisual rows.
- **D-17:** Phase 5 may replace or extend this resolver with a nutrition/grounding resolver. Keep the Phase 4.3 resolver contract intentionally small and easy to swap.

### UAT And Checkpoints
- **D-18:** Preserve the temporary UAT database checkpoint `mealttracker_uat_with_meal_embeddings` as a useful repeated-meal state for validation.
- **D-19:** Live UAT should prove that repeated-meal vector candidates influence reasoning, template questions are rendered, a partial reply re-prompts only missing required questions, and final save creates the expected DiaryEntry and FoodVisual rows.
- **D-20:** Langfuse traces should show the reasoning output schema, clarification schema, deterministic answer payloads, and final resolver payload, without relying on model-authored user-facing prompt text.

### the agent's Discretion
- The planner may choose exact Python model names and storage shape for clarification questions and answers as long as question IDs are stable and durable.
- The planner may choose whether root-level `top_3` removal is hard-cut or compatibility-shimmed, provided tests lock the new source of truth.
- The planner may choose exact Telegram rendering primitives inside the existing python-telegram-bot setup.

### Deferred Ideas (OUT OF SCOPE)
- Phase 5 owns SearXNG/Firecrawl tool loops and nutrition grounding.
- A full nutrition resolver or richer post-interview grounding agent belongs to Phase 5.
- Broader bot polish, slash commands, daily summaries, and result formatting remain Phase 6.

## Summary

The codebase already has the three 04.3 building blocks needed for a deterministic clarification rewrite: grouped reasoning with per-group candidates, DB-owned interview state, and a shared authoritative final write path. The remaining problem is architectural drift: `coerce_reasoning_response()` still synthesizes root `top_3`, `evaluate_reasoning_gate()` still returns it, and the current meal interview path still lets an LLM author user-facing turns. [VERIFIED: codebase grep]

The lowest-risk 04.3 design is: keep one grouped reasoning pass, add a compact `clarification_schema`, persist answers by stable `question_id`, render Telegram prompts from templates, and call a resolver-only LLM step only after all required answers are present. This preserves `meal_resolution_service.apply_final_meal_resolution()` as the sole writer of `FoodItem`, `DiaryEntry`, and `FoodVisual` rows. [VERIFIED: codebase grep]

**Primary recommendation:** Hard-cut root `top_3` as active logic inside reasoning/gating/persistence, keep only a short-lived read-side compatibility shim, and make `clarification_schema` plus `answers_by_question_id` the new deterministic interview contract. [VERIFIED: codebase grep]

### Pattern 1: Group-Owned Candidates With Read-Side Compatibility Only
**What:** Treat `food_groups[*].top_3` as the only live candidate source. Keep root `top_3` only as a temporary derived field at read boundaries for stale payloads/tests, because it is still synthesized today in `coerce_reasoning_response()` and `evaluate_reasoning_gate()`. [VERIFIED: codebase grep]
**When to use:** Immediately in 04.3 migration wave 1. [VERIFIED: codebase grep]
**Example:**

def active_top_three(group: dict[str, object]) -> list[dict[str, object]]:
    return [dict(candidate) for candidate in group.get("top_3", []) if isinstance(candidate, dict)][:3]

food_groups = normalized["food_groups"]
primary_group = food_groups[0] if food_groups else None
legacy_root_top_3 = active_top_three(primary_group) if primary_group else []

### Pattern 2: Compact `clarification_schema` With Stable Question IDs
**What:** Put a strict, compact `clarification_schema` beside `food_groups`, not inside user-facing transcript text. Recommended question fields are `question_id`, `group_id`, `primary_segment_id`, `segment_ids`, `question_kind`, `answer_type`, `required`, `choices`, and `validation`. IDs should derive only from stable structural fields, not prompt copy. [VERIFIED: codebase grep][ASSUMED]
**When to use:** For every unresolved group and every approval-needed group in 04.3. [CITED: .planning/phases/04.3-deterministic-clarification-schema-interview-ui/04.3-CONTEXT.md]
**Example:**
```python
# Source: recommended 04.3 schema shape built on current Pydantic strict-model pattern
class ClarificationChoice(BaseModel):
    model_config = ConfigDict(extra="forbid")
    choice_id: str
    label: str
    allows_free_text: bool = False

class ClarificationQuestion(BaseModel):
    model_config = ConfigDict(extra="forbid")
    question_id: str
    group_id: str
    primary_segment_id: str
    segment_ids: list[str]

    choices: list[ClarificationChoice] = Field(default_factory=list)
    validation: dict[str, int | bool | str | list[str]]
```

**What:** Do not let `run_interview_turn()` author prompts once deterministic questions exist. Either replace it with a smaller resolver contract, or call it only after all required questions are answered and reject any non-confirmation output. [VERIFIED: codebase grep][ASSUMED]
**When to use:** After deterministic answer collection is complete. [CITED: .planning/phases/04.3-deterministic-clarification-schema-interview-ui/04.3-CONTEXT.md]
**Example:**

    meal_reasoning=state["meal_reasoning"],

### Anti-Patterns to Avoid

- **Prompt-derived IDs:** Never derive `question_id` from rendered prompt text; copy changes would orphan saved answers. [ASSUMED]
- **Second source of truth for candidates:** Do not keep mutating both root `top_3` and group `top_3`; it reintroduces the 04.1/04.2 drift. [VERIFIED: codebase grep]
- **Resolver-authored follow-up questions:** If the resolver can ask a question, 04.3 has not actually removed freeform interview turns. [CITED: .planning/phases/04.3-deterministic-clarification-schema-interview-ui/04.3-CONTEXT.md]
- **PTB-only in-memory answer state:** Replies must survive restarts and stale prompt races, so DB state stays authoritative. [VERIFIED: codebase grep]

## Common Pitfalls

### Pitfall 1: Root `top_3` Quietly Stays Live
**What goes wrong:** New clarification code reads group candidates, but gate/persistence/tests still assert root `top_3`, so the old meal-level race logic lingers. [VERIFIED: codebase grep]
**Why it happens:** `coerce_reasoning_response()`, `evaluate_reasoning_gate()`, and `persist_reasoning_results()` still synthesize or return root `top_3`. [VERIFIED: codebase grep]
**How to avoid:** Remove root `top_3` from live branching first, then leave only a compatibility shim for stale reads. [VERIFIED: codebase grep]
**Warning signs:** Any new 04.3 code path still accessing `result["top_3"]` outside an explicit legacy adapter. [VERIFIED: codebase grep]

### Pitfall 2: Partial Replies Overwrite Prior Answers
**What goes wrong:** A user answers one question in a batch and the remaining required questions are lost or re-asked from scratch. [CITED: .planning/phases/04.3-deterministic-clarification-schema-interview-ui/04.3-CONTEXT.md]
**Why it happens:** Current state is keyed mostly by segment and transcript, not by `question_id`. [VERIFIED: codebase grep]
**How to avoid:** Persist answers by `question_id`, derive pending questions from required unanswered IDs, and append every user/bot step to `InterviewMessage`. [VERIFIED: codebase grep][ASSUMED]
**Warning signs:** A rerender drops already answered approvals or changes which question is considered complete after prompt copy edits. [ASSUMED]

### Pitfall 3: Buttons Without Durable Identity
**What goes wrong:** Inline buttons render, but callback payloads cannot be mapped back to a stable question/choice after retries or redeploys. [CITED: https://docs.python-telegram-bot.org/en/stable/telegram.ext.callbackqueryhandler.html]
**Why it happens:** Callback handlers route on `CallbackQuery.data`, so unstable or text-only payloads make replay brittle. [CITED: https://docs.python-telegram-bot.org/en/stable/telegram.ext.callbackqueryhandler.html]
**How to avoid:** Encode `question_id` and `choice_id` in callback data and mirror them into DB payloads. [CITED: https://docs.python-telegram-bot.org/en/stable/telegram.ext.callbackqueryhandler.html][ASSUMED]
**Warning signs:** A callback answer can only be interpreted from the currently rendered prompt text. [ASSUMED]

### Pitfall 4: Resolver Scope Creep Recreates 04.2
**What goes wrong:** The final resolver starts deciding what to ask next, so the deterministic UI becomes a thin wrapper over another freeform interview loop. [CITED: .planning/phases/04.3-deterministic-clarification-schema-interview-ui/04.3-CONTEXT.md]
**Why it happens:** `interview_turn_manager.py` currently owns `turn_action`, `assistant_prompt`, repair, and ready-to-confirm validation. [VERIFIED: codebase grep]
**How to avoid:** Call the resolver only when required answers are complete, and keep any follow-up selection deterministic in `interview_service.py`. [VERIFIED: codebase grep][ASSUMED]
**Warning signs:** The resolver still returns `continue_interview` or `need_clarification` for user-facing turns. [VERIFIED: codebase grep]

### Pitfall 5: Breaking Visual Learning on Confirmation
**What goes wrong:** The meal saves, but no `FoodVisual` rows are written, so repeated-meal UAT appears to “forget” prior answers. [VERIFIED: codebase grep]
**Why it happens:** Visual learning depends on `segment_embedding`, `segment_cropped_image_url`, and the authoritative final write path. [VERIFIED: codebase grep]
**How to avoid:** Keep `final_resolution_from_confirmation()` and `apply_final_meal_resolution()` in the path, and preserve segment IDs/embeddings when transforming deterministic answers into confirmation items. [VERIFIED: codebase grep]
**Warning signs:** The same meal reaches confirmation, but checkpointed repeated-meal reasoning does not see stronger vector candidates afterward. [VERIFIED: codebase grep]
