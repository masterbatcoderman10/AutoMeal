## Summary

Phase 04.1 should be implemented as a narrow contract-and-adapter correction, not a new reasoning subsystem. The current Phase 4 code already has the right ownership boundaries: one meal-level reasoning call, meal-owned aggregate state on `MealLog.reasoning_state_json`, DB-owned interview session state on `InterviewSession.current_prompt_payload`, and a shared final-write transaction in `apply_final_meal_resolution()`. [VERIFIED: codebase grep]

The concrete defect is structural, not cosmetic: `app/services/reasoning_schema.py` requires a single root `top_3`; `evaluate_reasoning_gate()` compares candidates inside that root list; `persist_reasoning_results()` copies that same list onto every segment; and `prepare_interview_session()` derives pending targets from raw segment labels, which produces the confusing interview observed in the Phase 4.1 UAT. [VERIFIED: codebase grep]

The corrective design is to make `food_groups` the strict source of truth, keep meal-level summary fields only for routing, persist one full grouped reasoning document per meal plus compact group snapshots per segment, and generate deterministic user-facing prompts from structured question hints rather than from raw segment labels or free-form LLM prose. [CITED: .planning/phases/04.1-grouped-reasoning-human-interview-correction/04.1-CONTEXT.md]

**Primary recommendation:** Replace the root `top_3` contract with required `food_groups[*].top_3`, add a group-to-final-resolution adapter ahead of `apply_final_meal_resolution()`, and retarget interview sessions to unresolved groups while preserving the existing Langfuse, DB, and final-write surfaces. [VERIFIED: codebase grep]

## Current Implementation Diagnosis

1. `reasoning_response_format()` hard-requires one root `top_3` array and `coerce_reasoning_response()` normalizes every payload back into that shape, so the current contract cannot express candidate competition per food group. [VERIFIED: codebase grep]
2. `_reasoning_system_prompt()` and `_build_reasoning_prompt()` explicitly instruct the model to return “exactly three `top_3` records” for the whole meal, which is why the observed UAT produced three unrelated foods as if they were alternatives. [VERIFIED: codebase grep]
3. `evaluate_reasoning_gate()` computes top-1, top-2, margin, missing evidence, and nutrition impact from the root `top_3` list, so it currently compares unrelated foods across the meal rather than candidates within one food decision. [VERIFIED: codebase grep]
4. `persist_reasoning_results()` writes the same `top_3`, `decision_rationale`, and `gate_reason` into every `MealSegment.ai_reasoning` row, which destroys per-segment/per-group audit value and directly violates Phase 4.1 decision D-06. [VERIFIED: codebase grep]
5. `prepare_interview_session()` builds `pending_targets` from `segment.id` and `segment.label` only, and `current_target_question()` starts from the raw label with wording like “Include the main food name and any key ingredient or preparation detail that changes nutrition,” which matches the robotic UAT complaint. [VERIFIED: codebase grep]
6. `finalize_meal_from_reasoning()` preserves the transaction boundary in `apply_final_meal_resolution()`, but the auto-confirm path currently builds `FinalSegmentResolution` objects from `match_results`, not from the reasoning payload. Grouped reasoning therefore needs an adapter before the existing writer, otherwise the new reasoning output will never reach persisted DiaryEntries or FoodVisuals. [VERIFIED: codebase grep]
7. `apply_final_meal_resolution()` writes one `DiaryEntry` per `FinalSegmentResolution`, so if grouped reasoning collapses overlapping segments into one food decision, the grouped adapter must emit one logical resolution per food group, not one per raw detector segment, or the phase will create duplicate diary rows. [VERIFIED: codebase grep]
8. Langfuse capture is already wired in two places: `llm_client.py` uses `langfuse.openai.AsyncOpenAI`, and `reasoning_service._run_reasoning_model()` also sends the exact request messages, response format, and raw output through `tracing_service.maybe_start_trace()`. The correction phase should preserve that path and only change payload contents. [VERIFIED: codebase grep]

### Anti-Patterns to Avoid

- **Root-list compatibility shim:** Do not keep root `top_3` as the effective source of truth and merely copy group data into an extra field; that would preserve the current incorrect gate behavior. [VERIFIED: codebase grep]
- **Per-segment prompt targeting:** Do not let `prepare_interview_session()` derive targets straight from `segment.label`; Phase 4.1 exists because that is the broken behavior. [VERIFIED: codebase grep]
- **One DiaryEntry per duplicate segment:** Do not emit one final resolution per overlapping detector crop when a grouped decision intentionally collapses them. [VERIFIED: codebase grep]
- **Prompt text authored by the model:** Do not make Telegram prompt wording depend on opaque LLM copy because it will be less deterministic, less auditable, and harder to keep human. [CITED: .planning/phases/04.1-grouped-reasoning-human-interview-correction/04.1-CONTEXT.md]

## Recommended Target Schema Shape

The strict response contract should move from `reasoning_contract_v1` to a grouped `reasoning_contract_v2` with these required top-level fields: `action`, `meal_state`, `trace_id`, `decision_rationale`, `gate_reason`, `segment_count`, `food_group_count`, and `food_groups`. [VERIFIED: codebase grep]

Each `food_group` should require `group_id`, `label`, `primary_segment_id`, `segment_ids`, `action`, `state`, `visual_evidence`, `missing_evidence`, `gate_reason`, `question_kind`, `question_focus`, `question_examples`, and `top_3`. [CITED: .planning/phases/04.1-grouped-reasoning-human-interview-correction/04.1-CONTEXT.md]

Each `food_group.top_3` record should preserve the existing candidate fields already normalized by `reasoning_schema.py`: `candidate_id`, `label`, `identity_confidence`, `quantity_confidence`, `match_consistency_confidence`, `visual_evidence`, `missing_evidence`, `specificity`, `nutrition_relevance`, `source`, `decision_rationale`, and `nutrition_impact`. Reusing that candidate shape minimizes schema churn and preserves existing gate math fields. [VERIFIED: codebase grep]

`group_id` should be deterministic inside one reasoning run and stable across persistence, for example by deriving it from ordered segment membership plus a sanitized label or internal ordinal. The exact algorithm is an implementation choice, but it must not depend on ephemeral Telegram state. [ASSUMED]

The root payload should not carry a required meal-wide `top_3` candidate list. If planner wants a compatibility field during rollout, keep it derived-only and never feed gate or interview logic from it. [CITED: .planning/phases/04.1-grouped-reasoning-human-interview-correction/04.1-CONTEXT.md]

## Persistence Strategy

### Meal-Level Auditability

- Store the full grouped reasoning document on `MealLog.reasoning_state_json["meal_reasoning"]`, including `food_groups`, `food_group_count`, `unresolved_group_ids`, `resolved_group_ids`, `ready_for_final_write`, `trace_id`, and `persisted_at`. `MealLog.reasoning_state_json` already exists and is the correct aggregation surface. [VERIFIED: codebase grep]
- Keep `ready_for_final_write` meal-owned, not segment-owned, because the existing finalization branch in `finalize_meal_from_reasoning()` already routes on that meal-level boolean. [VERIFIED: codebase grep]

### Segment-Level Auditability

- Replace the current duplicated `top_3` fan-out in `MealSegment.ai_reasoning` with a compact snapshot: `group_id`, `group_label`, `group_action`, `group_state`, `primary_segment_id`, `group_segment_ids`, `selected_candidate_id`, `candidate_ids`, and `trace_id`. This satisfies D-06 without storing the same whole-meal record N times. [CITED: .planning/phases/04.1-grouped-reasoning-human-interview-correction/04.1-CONTEXT.md]
- Keep `MealSegment.reasoning_trace_id` unchanged and continue writing the Langfuse/OpenRouter trace ID there when available. [VERIFIED: codebase grep]

### Interview-State Persistence

- Change `InterviewSession.current_prompt_payload["pending_targets"]` from `[{segment_id,label}]` to group-aware targets such as `[{group_id, primary_segment_id, segment_ids, label, question_kind, question_focus, question_examples, candidate_choices}]`. `InterviewSession.current_prompt_payload` is already the DB-owned recovery surface. [VERIFIED: codebase grep]
- Keep `answers_by_segment` backward-compatible during this phase by adding `group_id` and reusing `segment_id` as `primary_segment_id` where existing code still expects it. That minimizes churn in confirmation/edit flows. [ASSUMED]
- Preserve `InterviewMessage` logging of bot/user turns unchanged so the corrective phase does not disturb audit history or reminder behavior. [VERIFIED: codebase grep]

### Final Write Preservation

- Preserve `apply_final_meal_resolution()` as the only commit path for DiaryEntries, FoodVisuals, invalidations, and correction events. [VERIFIED: codebase grep]
- Insert a grouped adapter ahead of it that emits one `FinalSegmentResolution` per resolved food group, not per raw detector segment. Use the group's `primary_segment_id` to supply `segment_id`, `cropped_image_url`, and `embedding` to the unchanged writer. [VERIFIED: codebase grep]
- For overlapping duplicate groups, choose one representative segment as the write-back carrier and keep the full `segment_ids` only in reasoning JSON. This preserves the existing schema while preventing duplicate DiaryEntries. [ASSUMED]

## Interview Targeting And Prompt Strategy

- Target only unresolved groups where `food_group.action` is one of `INTERVIEW`, `ASK_CHOICE`, or `ASK_QUANTITY`. Do not enqueue already auto-confirmed groups. [CITED: .planning/phases/04.1-grouped-reasoning-human-interview-correction/04.1-CONTEXT.md]
- Sort pending group targets deterministically, with identity/detail questions before quantity questions, matching locked decision D-09. [CITED: .planning/phases/04.1-grouped-reasoning-human-interview-correction/04.1-CONTEXT.md]
- Generate prompt wording from structured fields, not raw labels alone. `question_kind=DETAIL` plus `question_focus="vegetable inside curry"` should produce the human wording pattern locked in D-12. [CITED: .planning/phases/04.1-grouped-reasoning-human-interview-correction/04.1-CONTEXT.md]
- Keep the roadmap backbone unchanged after the first prompt. The corrective work is mostly in the initial target/question construction, not in redesigning `SOURCE_TYPE`, `BRAND_NAME`, `RESTAURANT_NAME`, or `PORTION_CONTEXT`. [VERIFIED: codebase grep]
- For `ASK_CHOICE`, carry a compact `candidate_choices` list from `food_group.top_3` into the prompt payload so Telegram buttons or deterministic text can present meaningful alternatives within one group. [CITED: .planning/phases/04-reason-interview-learning-loop/04-CONTEXT.md]
- Keep the `/fix` path structurally separate. `/fix` already seeds a single targeted edit session from a DiaryEntry; Phase 4.1 should not merge meal-group interview state with correction-entry state. [VERIFIED: codebase grep]

## Common Pitfalls

### Pitfall 1: Keeping Root `top_3` Alive As Real Logic
**What goes wrong:** The planner adds `food_groups` but still leaves gate/interview/finalization keyed off the root candidate list. [VERIFIED: codebase grep]  
**Why it happens:** The current code has multiple root-`top_3` touchpoints in prompting, parsing, gating, fallback fill-in, and persistence. [VERIFIED: codebase grep]  
**How to avoid:** Cut over all policy decisions to `food_groups` in one wave: schema, gate, persistence, interview target generation, and final-write adapter. [VERIFIED: codebase grep]  
**Warning signs:** `evaluate_reasoning_gate()` still reads `normalized["top_3"]`, or `persist_reasoning_results()` still writes the same candidate list onto every segment. [VERIFIED: codebase grep]

### Pitfall 2: Breaking Phase 4 Final Writes While Fixing Reasoning
**What goes wrong:** Grouped reasoning produces better labels, but the completed meal still writes DB-match names because auto-confirm finalization still uses `match_results`. [VERIFIED: codebase grep]  
**Why it happens:** `finalize_meal_from_reasoning()` currently converts `match_results` into `FinalSegmentResolution` objects without consulting reasoning-selected group candidates. [VERIFIED: codebase grep]  
**How to avoid:** Add a group-to-resolution adapter and keep `apply_final_meal_resolution()` unchanged underneath it. [VERIFIED: codebase grep]  
**Warning signs:** The grouped payload contains better candidate labels than the final DiaryEntries. [VERIFIED: codebase grep]

### Pitfall 3: Duplicate DiaryEntries From Multi-Segment Groups
**What goes wrong:** A collapsed bread or curry group with two overlapping detector segments becomes two DiaryEntries. [VERIFIED: codebase grep]  
**Why it happens:** The current final writer creates one entry per `FinalSegmentResolution`. [VERIFIED: codebase grep]  
**How to avoid:** Emit one resolution per logical food group and keep only one representative `primary_segment_id` for write-back. [ASSUMED]  
**Warning signs:** `food_group.segment_ids` length is greater than 1, but the final write loop emits the same group multiple times. [ASSUMED]

### Pitfall 4: Letting Prompt Tone Depend On Raw Detector Labels
**What goes wrong:** The bot continues asking “What exactly should I log for it?” from raw segment labels even after grouped reasoning exists. [VERIFIED: codebase grep]  
**Why it happens:** `current_target_question()` currently starts from the current target label and a static generic template. [VERIFIED: codebase grep]  
**How to avoid:** Add `question_kind`, `question_focus`, and examples to the target payload and render the human prompt from those structured fields. [CITED: .planning/phases/04.1-grouped-reasoning-human-interview-correction/04.1-CONTEXT.md]  
**Warning signs:** Prompts still contain internal phrasing like `nutrition-relevant detail` or mention `segment` / `confidence`. [CITED: .planning/phases/04.1-grouped-reasoning-human-interview-correction/04.1-CONTEXT.md]

### Pitfall 5: Scope Bleed Into Phase 5
**What goes wrong:** The implementation starts adding SearXNG, Firecrawl, or broader nutrition derivation work while touching grouped reasoning. [CITED: .planning/phases/04.1-grouped-reasoning-human-interview-correction/04.1-CONTEXT.md]  
**Why it happens:** Grouped unresolved targets naturally resemble the later grounding problem. [CITED: .planning/ROADMAP.md]  
**How to avoid:** Preserve existing `NEEDS_GROUNDING` handoff state only; do not add tool calls, cost loops, or new nutrition enrichment in Phase 4.1. [VERIFIED: codebase grep]  
**Warning signs:** New tool schemas, new HTTP grounding calls, or new nutrition-write fields appear in the plan. [VERIFIED: codebase grep]

```python
# Source: recommended adapter in app/services/reasoning_service.py
def build_final_resolutions_from_food_groups(meal_reasoning, segments_by_id):
    final_segments = []
    for group in meal_reasoning["food_groups"]:
        if group["action"] not in {"AUTO_CONFIRM", "AUTO_CONFIRM_WITH_TRACE"}:
            continue
        primary = segments_by_id[group["primary_segment_id"]]
        selected = group["top_3"][0]
        final_segments.append(
            FinalSegmentResolution(
                food=ResolvedFoodInput(
                    canonical_name=selected["label"],
                    food_item_id=selected.get("food_item_id"),
                    llm_reasoning=group["gate_reason"],
                    is_verified=True,
                ),
                segment_id=primary.id,
                segment_cropped_image_url=primary.cropped_image_url,
                segment_embedding=primary.embedding,
                identification_method="AUTO_CONFIRM",
            )
        )
    return final_segments
```
