## User Constraints (from CONTEXT.md)

### Locked Decisions

### Per-Group Post-Processing Shape
- **D-01:** Run post-processing at the food-group level, not the whole-meal level. One finalized metadata payload should be produced per grouped food item.
- **D-02:** Fan out per-group finalizer calls in parallel with bounded concurrency. This is an orchestration step, not a serial loop over all groups.
- **D-03:** Each finalizer call must be scoped to one group's own context: grouped reasoning outcome, `top_3`, `group_actions`, selected clarifications, `segment_ids`, and any relevant crop refs or confirmation payload.
- **D-04:** The per-group finalizer must not ask new user-facing questions. It is a metadata composer only.
- **D-05:** The per-group finalizer output must be strict structured JSON and fail closed if malformed.

### Save-Ready Metadata Contract
- **D-06:** The finalizer output should be save-ready metadata for the existing authoritative transaction, not a replacement write path.
- **D-07:** At minimum, the finalizer output must include a proper final dish name, source type when known, quantity payload/display when known, portion bucket, and fields needed to create or update the learned FoodItem/FoodVisual record.
- **D-08:** Clarification answers that materially affect persistence must survive finalization. Bread count, source/origin, corrected identity, and user-provided free-text detail cannot be dropped.
- **D-09:** Final names should preserve food identity, not just answer fragments. A style answer like `Green masala` must not become the whole saved food name when the grouped food is clearly a chicken curry.
- **D-10:** The finalizer may emit alias/supporting metadata alongside the final name when that helps the learning loop, but the saved primary name must remain a dish-level identifier.

### Write Path Ownership
- **D-11:** `apply_final_meal_resolution()` remains the authoritative write path. Phase 4.4 should improve inputs to that transaction, not fork a second save system.
- **D-12:** Existing grouped clarification state in `MealLog.reasoning_state_json`, `InterviewSession.current_prompt_payload`, and durable answer payloads remains the source material for finalization.
- **D-13:** The finalizer should attach metadata needed to accompany visual learning before save, so the resulting FoodVisual/DiaryEntry pair reflects the clarified outcome instead of the pre-finalized fragment.
- **D-14:** If one group finalizer fails, the planner may choose a bounded retry and a per-group degraded fallback, but the failure policy must be explicit and testable. Silent lossy fallback is not acceptable.

### Model Decisions
- **D-15:** Use `google/gemini-3.1-flash-lite` for the new per-group post-processing/finalizer calls.
- **D-16:** Swap the detect/classification model default from `google/gemma-4-31b-it` to `google/gemini-3.1-flash-lite`.
- **D-17:** Keep the existing detect-stage structured contract and conservative fail-closed behavior; Phase 4.4 changes the model default, not the external detect interface.

### Scope Fence
- **D-18:** This is not Phase 5 grounding. Do not add SearXNG or Firecrawl calls, URL fetch loops, brand/restaurant nutrition search, or general web grounding.
- **D-19:** This is not a new freeform interview phase. The user-facing clarification UI stays deterministic as delivered in Phase 4.3.
- **D-20:** This phase exists to repair final metadata quality and preserve clarification answers before save, while keeping the Phase 4 authoritative transaction intact.

### the agent's Discretion
- The planner may choose the exact structured schema for per-group finalizer output as long as it is strict, compact, and sufficient for the existing save path.
- The planner may choose where bounded parallelism lives for the finalizer fan-out, as long as it reuses the current worker ownership boundaries and does not create a second background subsystem.
- The planner may decide whether quantity is represented as normalized JSON, a display string, or both internally, provided the persisted save path no longer drops user-supplied quantity answers.

### Deferred Ideas (OUT OF SCOPE)
- Phase 5 still owns web grounding, nutrition lookup, restaurant/brand fetch loops, and source attribution from external pages.
- Larger canonicalization, nutrition derivation, and alias expansion can build on Phase 4.4 later, but they are not required to ship the core fix for lossy post-clarification saves.
- Broader model rationalization across all stages beyond detect + per-group finalizer remains out of scope for this phase.

## Summary

The current lossy point is `interview_service.finalize_confirmed_interview()`: it converts each `confirmation_item` straight into `FinalSegmentResolution` and then calls `apply_final_meal_resolution()`, so any persistence-critical detail absent from `ConfirmationItem` is unrecoverable before the authoritative write. [VERIFIED: codebase grep]

The safest 04.4 shape is to keep the existing deterministic clarification UI, then add one compact LLM finalizer call per food group inside `finalize_confirmed_interview()`, aggregate the results, map them into `FinalSegmentResolution` objects in Python, and only then call `apply_final_meal_resolution()` once. This matches the locked decisions, preserves the current transaction boundary, and reuses the repo’s existing OpenRouter strict-JSON path. [VERIFIED: codebase grep][CITED: https://openrouter.ai/docs/guides/community/openai-sdk][CITED: https://openrouter.ai/docs/guides/features/structured-outputs]

The detect-model swap is low-risk because `poll_and_detect_food()` already passes a config string into `detect_food_photo()`, and the detect contract tests only assert the request shape and fail-closed threshold behavior, not Gemma-specific semantics. `google/gemini-3.1-flash-lite` is documented by OpenRouter as a GA multimodal model, and Google documents that Gemini 3.1 Flash-Lite supports structured outputs. [VERIFIED: codebase grep][CITED: https://openrouter.ai/google/gemini-3.1-flash-lite/api][CITED: https://ai.google.dev/gemini-api/docs/structured-output]

**Primary recommendation:** Add a dedicated `FINALIZER_MODEL` plus `FINALIZER_GROUP_PARALLELISM`, run per-group finalization inside `interview_service.finalize_confirmed_interview()` with `asyncio.Semaphore`-bounded fan-out and explicit per-group error capture, and keep `apply_final_meal_resolution()` as the only writer. [VERIFIED: codebase grep][CITED: https://docs.python.org/3.11/library/asyncio-sync.html][CITED: https://docs.python.org/3/library/asyncio-task.html]

### Pattern 3: Bounded Fan-Out Must Preserve Sibling Progress
**What:** Keep the repo’s existing bounded-concurrency pattern: one semaphore gates per-group work, while sibling groups can proceed if another group is slow. [VERIFIED: codebase grep]
**When to use:** For the per-group finalizer, not for the authoritative DB write. [VERIFIED: codebase grep]
**Example:**
```python
# Source: Python asyncio docs + current test_parallel_pipeline.py pattern
sem = asyncio.Semaphore(settings.FINALIZER_GROUP_PARALLELISM)

async def finalize_one(group_input):
    async with sem:
        return await call_group_finalizer(group_input)

results = await asyncio.gather(
    *(finalize_one(group_input) for group_input in group_inputs),
    return_exceptions=True,

```

### Anti-Patterns to Avoid

- **Reusing `ConfirmationItem` as the finalizer payload:** It preserves the current lossy shape and keeps quantity/supporting metadata too thin. [VERIFIED: codebase grep]
- **Letting the model author `FinalSegmentResolution` directly:** Embeddings, crop URLs, and visual-write flags are code-owned facts, not model outputs. [VERIFIED: codebase grep]
- **Saving each group independently:** The authoritative transaction is meal-scoped; partial per-group DB writes would fork persistence behavior. [VERIFIED: codebase grep]
- **Using `TaskGroup` without a deliberate failure policy:** Python documents that one exception cancels sibling tasks, which conflicts with explicit degraded per-group fallback. [CITED: https://docs.python.org/3/library/asyncio-task.html]

## Common Pitfalls

### Pitfall 1: Rich Answers Collapse Back Into Fragment Names
**What goes wrong:** Final names degrade into answer fragments such as `Green masala` or `Bran and whole wheat` instead of dish identities. [CITED: .planning/phases/04.4-parallel-group-finalization-lite-detect/04.4-CONTEXT.md]
**Why it happens:** The current save seam carries mostly approval-oriented `ConfirmationItem` fields, not a richer dish-level metadata contract. [VERIFIED: codebase grep]
**How to avoid:** Make the finalizer emit `final_name` plus optional aliases/supporting metadata, and keep Python-side mapping responsible for the final `ResolvedFoodInput`. [VERIFIED: codebase grep]
**Warning signs:** `confirmation_items[*].name` and saved `FoodItem.name` are identical even when clarification answers added cuisine/style/detail. [VERIFIED: codebase grep]

### Pitfall 2: Quantity Survives In State But Dies Before Save
**What goes wrong:** The user answers quantity, but `DiaryEntry.quantity_json` and `DiaryEntry.quantity_display` stay null. [CITED: .planning/phases/04.4-parallel-group-finalization-lite-detect/04.4-CONTEXT.md]
**Why it happens:** Quantity is currently too easy to lose between answer state and `FinalSegmentResolution` construction. [VERIFIED: codebase grep]
**How to avoid:** Make `quantity_json` and `quantity_display` explicit required-or-null fields in the finalizer output schema, and assert them in write-path tests. [VERIFIED: codebase grep]
**Warning signs:** `answers_by_question_id` contains quantity text while the outgoing `FinalSegmentResolution` does not. [VERIFIED: codebase grep]

### Pitfall 3: One Failed Group Cancels All Siblings
**What goes wrong:** A single finalizer exception aborts the whole meal, even though most groups could have been finalized or degraded independently. [CITED: https://docs.python.org/3/library/asyncio-task.html]
**Why it happens:** Raw `TaskGroup` semantics cancel siblings on first error, and raw `gather()` without explicit exception handling propagates failure to the waiter immediately. [CITED: https://docs.python.org/3/library/asyncio-task.html]
**How to avoid:** Wrap each group call, return structured success/failure results, and decide degraded fallback after fan-out completes. [CITED: https://docs.python.org/3/library/asyncio-task.html][CITED: https://docs.python.org/3.11/library/asyncio-sync.html]
**Warning signs:** Finalizer code has no per-group result envelope, no retry budget, or no persisted failure category. [VERIFIED: codebase grep]

### Pitfall 4: Detect Model Swap Stops At Config
**What goes wrong:** `DETECT_MODEL` changes, but unit tests, bot contract tests, and default wiring still assert Gemma strings. [VERIFIED: codebase grep]
**Why it happens:** The current tests hard-code `google/gemma-4-31b-it` in multiple places. [VERIFIED: codebase grep]
**How to avoid:** Update config defaults and the detect-path contract tests together in one wave. [VERIFIED: codebase grep]
**Warning signs:** `tests/test_vision_service.py` or `tests/test_bot_contract.py` still expect Gemma after the setting changes. [VERIFIED: codebase grep]

### Pitfall 5: Cross-Group Context Bleed
**What goes wrong:** One group’s clarification answer influences another group’s final name or source type. [CITED: .planning/phases/04.4-parallel-group-finalization-lite-detect/04.4-CONTEXT.md]
**Why it happens:** The finalizer prompt is fed meal-global transcript/state instead of one-group scoped inputs. [VERIFIED: codebase grep]
**How to avoid:** Build one authoritative input object per group and never include sibling-group answers except for immutable meal context if absolutely needed. [VERIFIED: codebase grep]
**Warning signs:** A finalizer input payload contains all `answers_by_question_id` entries instead of the subset for the active group. [VERIFIED: codebase grep]
