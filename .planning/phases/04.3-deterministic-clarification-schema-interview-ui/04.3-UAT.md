# 04.3 Live UAT Checklist

This checklist is the live operator runbook for the 04.3 resolver-only clarification flow. The run is only valid if it starts from the preserved repeated-meal checkpoint `mealttracker_uat_with_meal_embeddings`, exercises the repeated-meal Telegram flow end to end, and records both database deltas and Langfuse trace evidence.

## Preconditions

- `rtk docker compose ps` shows `postgres`, `api`, and `bot` available locally.
- Telegram delivery works for the pinned chat.
- Langfuse is reachable for trace lookup.
- You have the repeated-meal photo or iOS Shortcut path that previously produced:
  - `Egg Curry with Bottle Gourd`
  - `Chicken Drumstick in Green Phaal Curry`
  - `White Khubz`

## 1. Preserve Or Activate The Checkpoint

The saved checkpoint database must remain intact. Use one of these activation modes and record which one was used in `04.3-UAT-RESULTS.md`.

### Option A: Checkpoint Already Active

Use this only if the running `api` and `bot` are already pointed at the database cloned from `mealttracker_uat_with_meal_embeddings`.

Verification command:

```bash
rtk docker exec mealttracker-postgres psql -U mealttracker -d postgres -tAc "SELECT datname FROM pg_database WHERE datname='mealttracker_uat_with_meal_embeddings';"
```

### Option B: Clone The Checkpoint To A Disposable UAT Database

Recommended when you want to preserve `mealttracker_uat_with_meal_embeddings` and avoid touching the default `mealttracker` database.

```bash
rtk docker compose stop api bot
rtk docker exec mealttracker-postgres psql -U mealttracker -d postgres -c "DROP DATABASE IF EXISTS mealttracker_043_live WITH (FORCE);"
rtk docker exec mealttracker-postgres psql -U mealttracker -d postgres -c "CREATE DATABASE mealttracker_043_live TEMPLATE mealttracker_uat_with_meal_embeddings;"
```

Then start `api` and `bot` against `mealttracker_043_live` with a local, untracked compose override that changes both `DATABASE_URL` values from `/mealttracker` to `/mealttracker_043_live`.

Recommended redeploy command:

```bash
rtk docker compose -f docker-compose.yml -f docker-compose.uat-043-live.yml up -d --build --force-recreate api bot
```

### Option C: Restore Over A Disposable Default Database

Use this only if your local `mealttracker` database is already disposable and you explicitly want the default compose wiring.

```bash
rtk docker compose stop api bot
rtk docker exec mealttracker-postgres psql -U mealttracker -d postgres -c "DROP DATABASE IF EXISTS mealttracker WITH (FORCE);"
rtk docker exec mealttracker-postgres psql -U mealttracker -d postgres -c "CREATE DATABASE mealttracker TEMPLATE mealttracker_uat_with_meal_embeddings;"
rtk docker compose up -d --build --force-recreate api bot
```

## 2. Pre-Run Database Snapshot

Pick the active UAT database name (`mealttracker_043_live` if cloned, otherwise the database actually used by `api`/`bot`) and record it in `04.3-UAT-RESULTS.md`.

Baseline row-count commands:

```bash
rtk docker exec mealttracker-postgres psql -U mealttracker -d <ACTIVE_UAT_DB> -c "SELECT COUNT(*) AS diary_entries_before FROM diary_entries;"
rtk docker exec mealttracker-postgres psql -U mealttracker -d <ACTIVE_UAT_DB> -c "SELECT COUNT(*) AS food_visuals_before FROM food_visuals WHERE is_invalidated = false;"
rtk docker exec mealttracker-postgres psql -U mealttracker -d <ACTIVE_UAT_DB> -c "SELECT COUNT(*) AS embedded_segments_before FROM meal_segments WHERE embedding IS NOT NULL;"
```

Checkpoint sanity checks:

```bash
rtk docker exec mealttracker-postgres psql -U mealttracker -d <ACTIVE_UAT_DB> -c "SELECT COUNT(*) AS prior_repeat_meal_food_visuals FROM food_visuals WHERE is_invalidated = false;"
rtk docker exec mealttracker-postgres psql -U mealttracker -d <ACTIVE_UAT_DB> -c "SELECT COUNT(*) AS prior_repeat_meal_diary_entries FROM diary_entries;"
```

Expected checkpoint characteristics:

- `FoodVisual` rows already exist from the previous confirmed meal.
- `meal_segments.embedding` is populated for the repeated-meal crops.
- The checkpoint is rich enough for vector candidates to influence the next reasoning pass.

## 4. Execute The Repeated-Meal Scenario

Trigger the same meal flow used to seed `mealttracker_uat_with_meal_embeddings`.

### Live expectations before any reply

- The repeated meal should surface prior vector candidates in reasoning.
- Telegram prompts must come from deterministic templates, not freeform model-authored copy.
- The stored reasoning output must include `clarification_schema`.

### Required partial-reply sequence

1. Submit the repeated meal through the deployed iOS Shortcut or equivalent live ingest path.
2. Wait for the Telegram clarification flow to start.
3. Intentionally answer only the first available clarification step.
   - If the first prompt is a button-based approval or source-origin question, answer that one and stop.
   - Do not provide the final required free-text correction yet.
4. Verify the next Telegram prompt contains only the remaining required question(s).
   - Already-answered approvals must not loop.
   - The bot must not invent a new user-facing question from the resolver.
5. Answer the remaining required question(s).
   - The canonical repeated-meal path should end with names equivalent to `Egg Curry with Bottle Gourd`, `Chicken Drumstick in Green Phaal Curry`, and `White Khubz`.
6. Verify the confirmation message is rendered from `confirmation_items`.
7. Send `confirm` to trigger the authoritative save path.

## 5. Post-Confirmation Database Checks

Re-run the row-count queries against the same active UAT database:

```bash
rtk docker exec mealttracker-postgres psql -U mealttracker -d <ACTIVE_UAT_DB> -c "SELECT COUNT(*) AS diary_entries_after FROM diary_entries;"
rtk docker exec mealttracker-postgres psql -U mealttracker -d <ACTIVE_UAT_DB> -c "SELECT COUNT(*) AS food_visuals_after FROM food_visuals WHERE is_invalidated = false;"
```

Inspect the saved meal:

```bash
rtk docker exec mealttracker-postgres psql -U mealttracker -d <ACTIVE_UAT_DB> -c "SELECT id, processing_status, reasoning_state_json->'clarification_schema' AS clarification_schema, reasoning_state_json->'answers_by_question_id' AS answers_by_question_id, reasoning_state_json->'resolver_payload' AS resolver_payload FROM meal_logs ORDER BY created_at DESC LIMIT 1;"
rtk docker exec mealttracker-postgres psql -U mealttracker -d <ACTIVE_UAT_DB> -c "SELECT id, food_item_id, segment_id, is_verified, quantity_display FROM diary_entries ORDER BY created_at DESC LIMIT 6;"
rtk docker exec mealttracker-postgres psql -U mealttracker -d <ACTIVE_UAT_DB> -c "SELECT id, food_item_id, meal_segment_id, cropped_image_url FROM food_visuals ORDER BY created_at DESC LIMIT 6;"
```

Expected success conditions:

- `DiaryEntry` row count increases by the number of saved confirmation items. For the repeated-meal checkpoint, expect `+3`.
- `FoodVisual` row count increases for the confirmed items that still have embeddings. For the repeated-meal checkpoint, expect `+3`.
- The newest `meal_logs.reasoning_state_json` includes:
  - `clarification_schema`
  - `answers_by_question_id`
  - `resolver_payload`
- The save path reaches the authoritative writer used by `apply_final_meal_resolution()`.
