## Summary

The interview orchestration changes add the intended contracts and routing pieces, but the grouped-food grounding path is still broken and several prompt/state handling choices will degrade live behavior. I also found workflow/tooling defects in the preflight harness and session routing. Dynamic red-suite execution was not fully runnable in this environment because local Python dependencies such as `sqlalchemy` and `fastapi` are not installed.

## Critical Issues

### CR-01: Grouped confirmations deadlock post-interview grounding

**File:** `app/services/interview_schema.py:14-25`, `app/services/interview_turn_manager.py:165-177`, `bot/polling.py:160-208`, `bot/polling.py:637-658`
**Issue:** The interview contract only carries a single `segment_id` per confirmation item, and the turn validator only checks coverage by `group_id`. That works for grouped interview questions, but the post-interview grounding worker rebuilds candidates per `MealSegment`. For any grouped `PACKAGED` or `RESTAURANT` answer with multiple `segment_ids`, only the primary segment can be reconstructed; sibling segments are marked missing and `poll_post_interview_grounding()` writes `RETRY_PENDING` instead of ever reaching reasoning/finalization. No scoped test covers a multi-segment grouped grounding handoff, so this ships undetected.
**Fix:**
```python
# Preserve group membership in the confirmation contract.
class ConfirmationItem(BaseModel):
    group_id: str
    primary_segment_id: str
    segment_ids: list[str]
    segment_id: str
    ...

# Then expand one group confirmation across every segment in the group.
for item in confirmation_items:
    for segment_id in item["segment_ids"]:
        confirmation_by_segment[segment_id] = item
```

## Warnings

### WR-01: The newest user reply is injected into every LLM turn twice

**File:** `bot/handlers.py:582-607`, `bot/handlers.py:720-726`, `app/services/interview_turn_manager.py:201-209`
**Issue:** `_handle_meal_interview_turn()` appends the current user reply to `interview_messages` before calling the turn manager. `_run_meal_interview_turn()` then passes both the transcript and `latest_user_text`, and `_build_turn_messages()` appends the transcript entries and the latest user text again. The model therefore sees the same answer twice on every turn, which wastes context and can overweight the most recent reply.
**Fix:** Either call the turn manager before persisting the latest user message into `interview_messages`, or stop appending `latest_user_text` when the transcript already ends with that same user message.

### WR-02: Prompt construction is not bounded and leaks low-signal state into the model

**File:** `app/services/interview_turn_manager.py:46-54`, `app/services/interview_turn_manager.py:126-149`, `app/services/interview_turn_manager.py:195-209`
**Issue:** Every turn serializes the full `authoritative_state` into the prompt and trace payload, including ever-growing `interview_messages`, `segment_refs`, and local crop/image paths, then separately adds recent transcript entries. On repair it also embeds the entire raw response envelope. This violates the required bounded-context behavior, increases cost each turn, and makes prompt recovery depend on stale or irrelevant state.
**Fix:** Build a minimal authoritative snapshot for the model (`meal_id`, active unresolved groups, approval candidates, current question, summary) and exclude bulky fields like `interview_messages` and `segment_refs`. In repair mode, pass only the extracted invalid content plus the validation error, not the full response payload.

### WR-03: Meal interview startup can reuse an active `/fix` session for the same meal

**File:** `app/services/interview_service.py:524-535`, `app/services/interview_service.py:563-580`, `bot/polling.py:1201-1233`
**Issue:** `prepare_interview_session()` reuses any active session for the meal without checking `session_mode`. If an `ENTRY_FIX` session is active on the same `meal_log_id`, the poller will reuse it and `_start_meal_interview_turn()` will send meal-interview prompts into the fix session. `prepare_fix_interview_session()` also leaves incompatible active sessions alive when switching to a different entry, which increases ambiguity later.
**Fix:** Filter meal-session reuse to `SESSION_MODE_MEAL`, filter fix-session reuse to matching `SESSION_MODE_FIX` plus `fix_entry_id`, and deactivate incompatible active sessions before creating a new one.

### WR-04: Configuration failures are silently converted into hard-coded model routing

**File:** `app/services/interview_turn_manager.py:25-31`
**Issue:** `_resolve_settings()` catches every exception from `get_settings()` and substitutes baked-in defaults. Missing env, validation errors, or unrelated config bugs will therefore change model selection silently instead of failing closed. That breaks the pinned-model contract and makes deployment misconfiguration hard to detect.
**Fix:** Remove the blanket fallback from production code. Require explicit `settings` injection in tests, or catch only the narrow exception you intentionally want to tolerate.

### WR-05: Grounding handoff sends the same user notification twice

**File:** `bot/handlers.py:491-495`, `bot/handlers.py:661-665`, `bot/polling.py:517-520`
**Issue:** The handler already tells the user that the next step was queued when confirmation returns `grounding_required`. The background handoff worker sends the same `format_grounding_pending_message()` again before it flips the handoff state. Users will receive duplicate “queued the next step” messages for every grounded interview.
**Fix:** Make a single layer responsible for user notification. The simplest fix is to keep the message in the handler and let `poll_grounding_handoffs()` mutate persistence state only.

### WR-06: The preflight harness rejects a supported runtime and cannot select the interpreter it requires

**File:** `scripts/assert_phase_04_2_preflight.py:39-44`, `scripts/assert_phase_04_2_preflight.py:63-74`, `scripts/assert_phase_04_2_preflight.py:102-109`
**Issue:** The stack guidance allows Python 3.12 or 3.13, but `_assert_python_version()` exits unless the venv interpreter is exactly 3.12. Worse, `_ensure_venv()` creates `.venv` with whatever interpreter launched the script, so on machines where `python3` is 3.13 or 3.14 the script creates a doomed environment and then aborts.
**Fix:** Accept both supported versions or probe for a specific interpreter before creating the venv, for example:
```python
SUPPORTED = {(3, 12), (3, 13)}
if (payload.get("major"), payload.get("minor")) not in SUPPORTED:
    raise SystemExit(...)
```
