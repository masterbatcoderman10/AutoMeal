## 1. System Classification

**System Type:** Hybrid - conversational turn manager + structured extraction

**Description:**
Phase 04.2 replaces the deterministic Telegram interview continuation with an LLM-assisted turn manager. It consumes durable grouped reasoning context, prior assistant/user transcript history, unresolved food targets, and clear approval candidates, then returns one strict structured action: continue the interview, ask for targeted clarification, or produce normalized confirmation items for the existing final write-back path.

**Critical Failure Modes:**
1. A natural answer such as "bottle gourd" is treated as a literal standalone food name instead of resolving the intended egg/vegetable curry target.
2. A Telegram reply is routed to a stale active interview session instead of the meal/thread the user is answering.
3. Clear/high-confidence food groups are omitted from the interview context and never receive explicit approval or correction.
4. Invalid or incomplete model JSON reaches final write-back without strict Pydantic validation and bounded repair.
5. The LLM bypasses `finalize_confirmed_interview()` / `apply_final_meal_resolution()` and writes FoodItems, DiaryEntries, or FoodVisuals directly.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Consumer wellness / personal nutrition tracking

**User Population:** A single self-tracking user logging home-cooked, packaged, and restaurant meals from photos, then correcting or confirming them through Telegram.

**Stakes Level:** Medium

**Output Consequence:** The interview output becomes `DiaryEntry` nutrition records and also teaches the future visual vocabulary. A wrong result distorts the current meal log and can poison future auto-matches; a missed confirmation leaves the diary incomplete.

### What Domain Experts Evaluate Against

Dimension: Mixed-dish resolution in context  
Good (domain expert would accept): When the user answers with an ingredient or modifier like `bottle gourd`, `pita`, or `chicken leg`, the system resolves it against the active dish and returns a normalized meal item such as `egg curry with bottle gourd` rather than treating the fragment as a standalone food.  
Bad (domain expert would flag): The system logs the reply literally as the food name, or asks a redundant naming question like `What should I call pita?` after the meal context already makes the intent clear.  
Stakes: High  
Source: Dietary assessment literature repeatedly treats mixed dishes, hidden ingredients, and food classification as core sources of dietary-record error; this phase's trigger defect is exactly a mixed-dish resolution failure.

Dimension: Coverage of all meal items needing approval  
Good (domain expert would accept): The interview includes both unclear items and already-confident items that still need user approval, so the user can correct a wrong `pita bread` or `chicken curry` in the same turn.  
Bad (domain expert would flag): The assistant asks only about the ambiguous curry detail and silently commits other meal items without explicit confirm/correct opportunity.  
Stakes: High  
Source: Dietary assessment error frameworks emphasize omission, intrusion, and misclassification; in this product, omission of clear items from the approval turn creates the same downstream error.

Dimension: Nutrition-relevant follow-up with low user burden  
Good (domain expert would accept): Each follow-up asks only for the next detail that materially changes logging quality, such as dish identity, home vs packaged vs restaurant source, brand/restaurant name, or coarse portion bucket. The prompt is brief and answerable in everyday language.  
Bad (domain expert would flag): The assistant asks robotic, developer-centric, or redundant questions, collects details that do not change the logged record, or forces a long interview for a simple meal.  
Stakes: Medium  
Source: Image-assisted dietary assessment is valuable partly because it lowers logging burden, while still needing targeted follow-up when images alone are insufficient.

Dimension: Conservative handling of quantity and certainty  
Good (domain expert would accept): The system does not invent precise amounts or nutrition from a single ambiguous photo. If quantity is still uncertain, it asks for or records a bounded portion bucket and preserves uncertainty until the authoritative write-back step.  
Bad (domain expert would flag): The system overconfidently infers exact serving size, exact macros, or unsupported preparation details from the conversation alone.  
Stakes: High  
Source: Portion estimation remains a hard problem in image-based dietary assessment because a 2D image does not reliably encode volume, density, or preparation details.

Dimension: Thread-safe confirmation integrity  
Good (domain expert would accept): A Telegram reply updates only the intended meal/thread, and the LLM emits structured confirmation items for the existing finalization path rather than directly mutating diary or visual-memory records.  
Bad (domain expert would flag): A stale session steals a reply, or a malformed/overreaching model response causes the wrong meal to be confirmed, corrected, or learned.  
Stakes: Critical  
Source: In this domain, diary correctness depends on meal-level provenance; this phase's acceptance criteria explicitly require reply scoping and authoritative write-back preservation.

### Known Failure Modes in This Domain

- Mixed-dish decomposition failure: an ingredient answer is logged as the whole dish, or a component detail is lost inside a generic label like `curry`.
- Omission/intrusion error: one meal component is never surfaced for approval, or an unsupported item is confirmed because the system over-trusts prior reasoning.
- Portion/source overconfidence: a single photo leads to an unjustified portion call or the wrong home/packaged/restaurant source, which shifts nutrition materially.
- Cross-meal thread contamination: a free-text reply attaches to the wrong active interview and corrupts the wrong diary entry.

### Regulatory / Compliance Context

No clinical or dietitian-practice regulation appears directly triggered for the current deployment context: this is a single-user self-use wellness logger, not a diagnosis or treatment system. HIPAA generally does not apply when a consumer app developer is not acting for a covered entity or business associate. FDA guidance treats many calorie-intake and healthy-lifestyle tracking apps as general wellness / low-risk use unless the product makes higher-risk medical claims.

The directly relevant compliance risk is privacy and security of health-adjacent personal data. If this product is commercialized, syncs data from multiple health sources, or experiences an unauthorized disclosure, FTC Act representations and the FTC Health Breach Notification Rule may become relevant even where HIPAA does not.

## 2. Framework Decision

**Selected Framework:** No new AI framework; direct OpenAI Python SDK 1.55.x via OpenRouter Chat Completions + Pydantic 2 strict-schema orchestration

**Version:** `openai==1.55.3`, `pydantic==2.10.3`, `langfuse==4.7.0`

**Rationale:**
This phase is a bounded, stateful interview turn manager over existing `InterviewSession` and `InterviewMessage` persistence, not an open-ended agent system. The repository already has the right OpenRouter-compatible Chat Completions transport, Langfuse tracing, strict JSON Schema support, and Pydantic validation patterns. Adding LangChain, CrewAI, OpenAI Agents SDK, or Google ADK would increase abstraction while weakening explicit state ownership and final write-path control.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| LangGraph | Useful if interview branching grows into a complex persisted graph, but overkill for a three-action turn contract in Phase 04.2. |
| OpenAI Agents SDK | Optimized for OpenAI-native agents, while this project is OpenRouter-only and needs no handoffs or agent runtime. |
| Google ADK | Gemini-oriented but adds a new session/memory framework when the repo already persists interview state in Postgres. |
| CrewAI | Multi-agent role orchestration does not match a single Telegram clarification turn manager. |

**Vendor Lock-In Accepted:** Partial - model access is OpenRouter-only by project constraint, while the code stays on the OpenAI-compatible Chat Completions shape and Pydantic schemas to preserve provider flexibility.

```python
from __future__ import annotations

import json
from typing import Any, Literal

from pydantic import BaseModel, ConfigDict

from app.services.llm_client import get_llm_client


class ConfirmationItem(BaseModel):
    model_config = ConfigDict(extra="forbid")

    group_id: str
    primary_segment_id: str
    decision: Literal["confirmed", "corrected"]
    canonical_name: str
    source_type: Literal["HOME", "PACKAGED", "RESTAURANT"]
    brand_name: str | None
    restaurant_name: str | None
    portion_bucket: Literal["SMALL", "STANDARD", "LARGE"] | None
    quantity_display: str | None
    correction_note: str | None


class InterviewTurnResult(BaseModel):
    model_config = ConfigDict(extra="forbid")

    turn_action: Literal[
        "continue_interview",
        "need_clarification",
        "ready_to_confirm",
    ]
    assistant_prompt: str
    clarification_reason: str | None
    conversation_summary: str | None
    confirmation_items: list[ConfirmationItem]


def strict_response_format(model: type[BaseModel], name: str) -> dict[str, Any]:
    return {
        "type": "json_schema",
        "json_schema": {
            "name": name,
            "strict": True,
            "schema": model.model_json_schema(),
        },
    }


def extract_message_content(response: dict[str, Any]) -> str:
    return str(response["choices"][0]["message"]["content"])


async def run_interview_turn(
    *,
    model: str,
    authoritative_state: dict[str, Any],
    transcript: list[dict[str, str]],
    latest_user_text: str,
) -> InterviewTurnResult:
    llm_client = get_llm_client()
    messages = [
        {
            "role": "system",
            "content": (
                "You are MealTracker's interview turn manager. "
                "Return strict JSON only. "
                "Choose exactly one action: continue_interview, "
                "need_clarification, or ready_to_confirm. "
                "Do not write database state and do not invent nutrition facts."
            ),
        },
        {
            "role": "system",
            "content": (
                "AUTHORITATIVE_STATE_JSON:\n"
                f"{json.dumps(authoritative_state, ensure_ascii=True, separators=(',', ':'))}"
            ),
        },
        *transcript[-6:],
        {"role": "user", "content": latest_user_text},
    ]
    response = await llm_client.chat_completion(
        model=model,
        messages=messages,
        response_format=strict_response_format(InterviewTurnResult, "interview_turn_v1"),
        max_tokens=1200,
    )
    return InterviewTurnResult.model_validate_json(
        extract_message_content(response),
        strict=True,
    )
```

### Key Abstractions
| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| `langfuse.openai.AsyncOpenAI` | OpenAI Python SDK surface instrumented for Langfuse | Every OpenRouter chat call in this repo |
| `response_format={"type":"json_schema", ...}` | Provider-enforced structured output contract | Every turn that can change interview state or trigger finalization |
| `BaseModel.model_json_schema()` | Pydantic schema source of truth | Build the strict response contract from Python models |
| `InterviewSession.current_prompt_payload` | Durable authoritative state for the active meal/thread | Source of truth for unresolved groups, approval groups, routing metadata, and summaries |
| `InterviewMessage` | Durable per-turn transcript | Persist each bot/user turn and rebuild bounded transcript context |

### Common Pitfalls
1. Using `chat.completions.parse()` in this phase is a poor fit for the current repo shape because the shared client returns dumped completion dictionaries.
2. Passing raw Pydantic schemas with defaults and loose optional fields makes strict mode brittle. Prefer required fields with nullable values and set `extra="forbid"` on every nested model.
3. Letting free-form assistant text become state is unsafe. The LLM may emit only one of three actions, and `ready_to_confirm` still flows through `finalize_confirmed_interview()` and `apply_final_meal_resolution()`.
4. Sending the full reasoning payload and full transcript every turn will inflate tokens and anchor the model on stale context. Send compact authoritative state plus the last 6-8 turns.
5. Routing replies to "latest active session" is not enough. Persist prompt/message scope and thread metadata so stale interviews cannot steal a Telegram reply.
6. OpenRouter's current docs show `X-OpenRouter-Title`; the repo currently sends `X-Title`. Verify header alias behavior before treating app-attribution headers as current.

## 4. Implementation Guidance

**Model Configuration:**
- Primary turn model: `google/gemini-3.1-flash-lite`
- Repair/fallback model: `google/gemini-3-flash-preview`
- Call shape: `chat.completions.create(...)` through `OpenRouterClient.chat_completion(...)`
- `response_format`: strict JSON schema from Pydantic
- `max_tokens`: `1200` for primary turns, `1600` for repair retry
- `stream`: `False`
- `tools`: `None` in Phase 04.2
- `temperature`: add pass-through support to `OpenRouterClient.chat_completion()` and set `0.1` for normal turns, `0.0` for repair retry

**Core Pattern:**
Use one authoritative state object per session turn, not free-form conversation as the system of record. Persist the user message first, build a compact state snapshot from `InterviewSession.current_prompt_payload` plus grouped reasoning output, call the model once, validate strictly, retry once on schema/domain failure, and only then either persist the next prompt or hand off to `finalize_confirmed_interview()`.

```python
def validate_turn_contract(
    *,
    turn: InterviewTurnResult,
    expected_group_ids: set[str],
) -> None:
    if turn.turn_action == "ready_to_confirm":
        returned_group_ids = {item.group_id for item in turn.confirmation_items}
        if returned_group_ids != expected_group_ids:
            raise ValueError(
                "ready_to_confirm must cover every active group: "
                f"expected={expected_group_ids}, got={returned_group_ids}"
            )
    elif not turn.assistant_prompt.strip():
        raise ValueError("non-final actions must include assistant_prompt")


async def orchestrate_interview_turn(
    *,
    session,
    meal,
    interview,
    segments: list[Any],
    authoritative_state: dict[str, Any],
    transcript: list[dict[str, str]],
    latest_user_text: str,
    primary_model: str = "google/gemini-3.1-flash-lite",
    fallback_model: str = "google/gemini-3-flash-preview",
) -> InterviewTurnResult | dict[str, Any]:
    active_group_ids = {
        str(group["group_id"])
        for group in authoritative_state["active_groups"]
    }
    messages = build_interview_messages(
        authoritative_state=authoritative_state,
        transcript=transcript,
        latest_user_text=latest_user_text,
    )

    with tracing_service.maybe_start_trace(
        name="interview_turn",
        input={
            "meal_id": meal.id,
            "session_id": interview.id,
            "models": [primary_model, fallback_model],
            "latest_user_text": latest_user_text,
        },
        metadata={
            "meal_id": meal.id,
            "session_id": interview.id,
            "chat_id": interview.chat_id,
        },
        span_name="interview_turn",
    ) as trace:
        turn = await call_and_validate_interview_turn(
            messages=messages,
            response_format=strict_response_format(InterviewTurnResult, "interview_turn_v1"),
            primary_model=primary_model,
            fallback_model=fallback_model,
            expected_group_ids=active_group_ids,
        )
        trace.end(output={"turn_action": turn.turn_action})

    if turn.turn_action == "ready_to_confirm":
        return await finalize_confirmed_interview(
            session=session,
            meal=meal,
            confirmation_items=[
                item.model_dump(mode="python")
                for item in turn.confirmation_items
            ],
            segments=segments,
        )
    return turn
```

**Tool Use:**
Phase 04.2 must not enable OpenRouter tools. This turn manager is not a grounding agent. Use `tools=None`, keep `parallel_tool_calls=False`, and do not call SearXNG or Firecrawl here. Post-interview grounding remains the existing downstream path for packaged and restaurant items.

**State Management:**
- `InterviewSession.current_prompt_payload` remains the authoritative session state. Expand it with `active_groups`, `approval_groups`, `current_focus_group_id`, `conversation_summary`, and `route_scope`.
- `route_scope` should include `chat_id`, `prompt_message_id`, and `turn_index`.
- `InterviewMessage` remains the durable transcript. Persist every user message before the LLM call and every assistant prompt after validation.
- `ready_to_confirm` must not write `FoodItem`, `DiaryEntry`, or `FoodVisual` directly.
- Add domain validation after Pydantic parse. Reject schema-valid but contradictory payloads such as missing groups, duplicate group IDs, blank prompts for non-final actions, or source-specific fields that contradict `source_type`.

**Context Window Strategy:**
- Send one compact state JSON object, not raw ORM dumps.
- Include only unresolved groups, clear groups needing approval, selected answers so far, the latest conversation summary, and the last 6-8 assistant/user turns.
- Exclude raw embeddings, full top-3 reasoning blobs, image payloads, and old prompts already captured in the summary.
- Summarize older turns into `conversation_summary` once the transcript exceeds 6 turns or about 2.5k input tokens.
- Keep the target prompt under roughly 3k input tokens per turn.

## 4b. AI Systems Best Practices

> Written by `gsd-ai-researcher`. Cross-cutting patterns every developer building AI systems needs — independent of framework choice.

### Structured Outputs with Pydantic

Use Pydantic as the contract source of truth, then pass `model.model_json_schema()` through `response_format={"type":"json_schema","json_schema":{...}}`. In this stack, do not use LangChain `.with_structured_output()` or `instructor`; the correct integration is direct OpenAI-compatible Chat Completions through the existing OpenRouter client.

Integration notes:
- Framework integration for this phase: `llm_client.chat_completion(..., response_format=strict_response_format(InterviewTurnResult, "interview_turn_v1"))`
- Set `extra="forbid"` on every nested model.
- Prefer required nullable fields over omitted optional fields so the model always returns the full shape.
- Keep schema rules simple. Use descriptions, enums, arrays, objects, `required`, and `additionalProperties: false`; enforce detailed constraints after parsing.

Retry policy:
- Attempt 1: primary model normal turn prompt.
- Attempt 2: one repair retry on `google/gemini-3-flash-preview`, with the invalid JSON attached and a "repair to strict JSON only" system instruction.
- Log `meal_id`, `session_id`, `chat_id`, `turn_index`, model slug, raw model payload, validation errors, and trace ID.
- After two failures, surface a safe fallback message and leave the meal in interview state. Do not finalize or write partial confirmations.

### Async-First Design

This stack is already async-first: FastAPI, SQLAlchemy async sessions, PTB async handlers, and `langfuse.openai.AsyncOpenAI`.

Rules:
- Keep the entire turn path `async def` end-to-end.
- Do not call `asyncio.run()` inside FastAPI handlers, PTB handlers, or scheduler jobs; the code is already inside an event loop.
- Await the full chat completion response for this phase. Streaming is unnecessary because the result must pass full JSON validation before it is usable.
- If streaming is added to user-facing prose later, keep structured extraction turns non-streaming.

### Prompt Engineering Discipline

- Keep system and user content separate.
- System prompt should contain only stable rules: one of three actions, no direct writes, no invented nutrition, and every active group must be resolved before finalization.
- Put authoritative structured state in a separate system message as compact JSON.
- Use the Telegram reply itself as the user message, not a rewritten paraphrase.
- Keep 2-3 inline few-shot examples for the target repairs: `bottle gourd` resolving egg/vegetable curry, `pita` confirming bread type, and `chicken leg` composing chicken curry.
- Set `max_tokens` explicitly on every call.

### Context Window Management

For this hybrid conversational + structured extraction flow:
- Keep the grouped reasoning output as the canonical upstream summary, not the full raw reasoning transcript.
- Include only active unresolved groups and clear groups needing approval.
- Cap transcript inclusion to the last 6-8 turns.
- Maintain a rolling `conversation_summary` after the transcript grows beyond 6 turns.
- Never drop `group_id`, `primary_segment_id`, current approved/corrected answer state, or route metadata.

### Cost and Latency Budget

Using the project's captured OpenRouter pricing for 2026-05-24:
- `google/gemini-3.1-flash-lite`: about `$0.25/M` input and `$1.50/M` output.
- `google/gemini-3-flash-preview`: about `$0.50/M` input and `$3.00/M` output.
- A typical turn at about 2.5k input tokens and 300 output tokens is roughly `$0.0011` on flash-lite and `$0.0022` on flash-preview.

Routing and caching:
- Use deterministic local fast paths for `same`, `yes`, `no`, and explicit `home/packaged/restaurant` replies only when the active state makes the answer unambiguous.
- Use `google/gemini-3.1-flash-lite` for normal turn management and summaries.
- Use `google/gemini-3-flash-preview` only for repair retry or hard ambiguous turns.
- Exact-match cache only for duplicate Telegram delivery/retried events keyed by `(session_id, turn_index, normalized_user_text, prompt_version, state_hash)`.
- Do not semantic-cache `ready_to_confirm` outputs because they are meal-specific.

- Code-based evals are the default gate. Store gold conversation fixtures and expected structured outputs for Phase 04.2, then compare normalized results deterministically in `tests.test_interview_flow`, `tests.test_bot_contract`, `tests.test_fix_flow`, and `tests.test_reasoning_flow`.
- Langfuse traces are the source of truth for production conversation capture, prompt/version comparison, repair-rate measurement, latency, token cost, and smart sampling.
- LLM judge is offline only for prompt quality and burden scoring. It is not a release gate until calibrated against human ratings with at least `0.7` agreement on a held-out sample.
- Human review is required for mixed-dish cultural normalization, calibration of the burden judge, and any write-back/routing anomaly.

**CI/CD Integration:**
```bash
python3.12 -m unittest tests.test_interview_flow tests.test_bot_contract tests.test_fix_flow tests.test_reasoning_flow -q
```

### Reference Dataset

**Size:** Start with `12` labeled examples during implementation; expand to `20` before production sign-off.

**Composition:**
- `3` critical mixed-dish resolution cases:
  - `It's bottle gourd` resolving an egg/vegetable curry target.
  - `pita` resolving a bread target without redundant renaming.
  - `chicken leg` resolving a chicken curry target.
- `2` approval-coverage cases where clear items such as `pita bread` and `chicken curry` must still be surfaced for confirm/correct in the same turn.
- `2` thread-routing cases: stale active session present but reply belongs to a newer prompt, and ambiguous free-text reply with no safe owner that must fail closed.
- `2` structured-output robustness cases: invalid JSON repaired successfully on bounded retry, and invalid/contradictory JSON rejected with no mutation.
- `2` authoritative write-back cases: `ready_to_confirm` flows through `finalize_confirmed_interview()`, and correction path preserves `USER_CORRECTED` semantics without direct writes.
- `1+` low-burden clarification case covering source type or portion bucket without over-asking.

**Labeling:**
- Code-labeled fields: expected `turn_action`, normalized confirmation items, required covered `group_id`s, allowed/forbidden source fields, expected finalizer invocation, and expected routing outcome.
- Human-labeled fields: whether the resulting meal name matches what was actually eaten, whether the follow-up was concise and useful, and whether the burden felt acceptable.
- Reviewers: primary user/product owner for correctness and burden, cuisine-familiar reviewer for dish normalization, backend owner for routing and authoritative write-back expectations.
- Creation timeline: every acceptance example from `04.2-CONTEXT.md` becomes a regression fixture before phase sign-off; every production routing, JSON repair, or mixed-dish incident is added to the dataset in a follow-up change.

## 6. Guardrails

### Online (Real-Time)

| Guardrail | Trigger | Intervention |
|-----------|---------|--------------|
| Reply-routing ownership guard | The incoming Telegram reply cannot be safely mapped to exactly one active interview by pinned chat plus prompt/message scope, or it matches a stale session instead of the intended prompt | Block mutation, leave sessions unchanged, send a safe clarification asking the user to reply to the latest meal prompt, and log a Langfuse trace with routing metadata |
| Strict schema and domain validation gate | The model response fails Pydantic validation, misses required groups, includes duplicate/conflicting confirmation items, or violates non-final prompt rules | Retry once with repair prompt; if still invalid, fail closed, persist no confirmation state, send a neutral retry message, and mark the turn as validation failure in Langfuse |
| Authoritative write-path guard | Any `ready_to_confirm` path bypasses `finalize_confirmed_interview()` / `apply_final_meal_resolution()`, or confirmation code path is missing authoritative finalizer invocation | Raise immediately, block all writes from that turn, keep the session open, and emit an operational alert |
| Unsupported nutrition/safety output guard | Assistant prompt contains exact macro/calorie claims, medical advice, or content outside meal clarification scope | Suppress the prompt, replace with a neutral clarification request, and log for review |

### Offline (Flywheel)

| Metric | Sampling Strategy | Action on Degradation |
|--------|------------------|----------------------|
| Mixed-dish resolution accuracy | Score all labeled reference fixtures on every CI run; sample all live turns containing short ingredient-only replies during initial rollout | Add new few-shot or state fields, then expand fixture coverage for the failed cuisine pattern |
| Approval coverage rate | Measure on every `ready_to_confirm` event and every reference dataset run | Treat any miss as a release blocker; add regression test before next deploy |
| Repair-rate and schema-failure trend | Review 100% of repair retries and all failed repairs from Langfuse traces weekly | Tighten schema, simplify prompt/state payload, or demote model/path if failures rise |
| Interview burden | Human-review all conversations with more than `4` turns plus a 20% random sample of successful sessions; use LLM judge only after calibration | Trim redundant questions, shorten prompt wording, or add deterministic fast paths for obvious answers |
| Routing anomaly rate | Review 100% of blocked ambiguous/stale routing events | Fix route-scope persistence or prompt-message binding before widening rollout |

## 7. Production Monitoring

**Tracing Tool:** Existing self-hosted Langfuse, using the current `langfuse.openai.AsyncOpenAI` client in `app/services/llm_client.py` and explicit span creation in `app/services/tracing_service.py`.

**Key Metrics to Track:**
- `interview_turn_validation_failure_rate`: percent of turns that fail schema/domain validation after the primary model call.
- `interview_turn_repair_rate`: percent of turns requiring the one allowed repair retry.
- `ready_to_confirm_group_coverage_failures`: count of turns where active groups are not covered exactly once.
- `routing_block_count`: count of stale/ambiguous reply-routing blocks.
- `finalizer_success_rate`: percent of `ready_to_confirm` turns that complete through the authoritative finalizer path without exception.
- `median_turns_to_resolution` and `p95_turns_to_resolution`: burden proxy for how many turns a meal needs before completion.
- `turn_latency_ms`, `tokens_per_turn`, and `usd_cost_per_turn`: operational drift metrics from traced model calls.

**Alert Thresholds:**
- Page immediately on any authoritative write-path bypass attempt or any cross-session routing mutation: threshold `> 0`.
- Alert on any `ready_to_confirm_group_coverage_failures`: threshold `> 0`.
- Alert if `routing_block_count > 1` in 24 hours.
- Alert if `interview_turn_validation_failure_rate > 5%` over the last `50` turns.
- Alert if `interview_turn_repair_rate > 15%` over the last `50` turns.
- Investigate if `median_turns_to_resolution > 4` or `p95_turns_to_resolution > 6` over the last `20` completed interviews.
- Investigate if traced interview turns are missing Langfuse `trace_id` for `3` consecutive turns.

**Smart Sampling Strategy:**
- Trace `100%` of interview turns in Langfuse.
- Human-review `100%` of blocked routing events, failed repairs, finalizer exceptions, correction flows, and conversations with more than `4` turns.
- During the first `20` live interview sessions, human-review `100%` of mixed-dish shorthand cases similar to `bottle gourd`, `pita`, and `chicken leg`.
- After rollout stabilizes, human-review `20%` random sample of successful sessions and `100%` of sessions with repair retry, routing ambiguity, contradictory confirmations, or unusually high token/latency cost.
- Use Langfuse metadata for review prioritization: repair retry used, non-final clarification loop, correction path hit, route-scope mismatch, missing approval candidate, high turn count, or unusually long assistant prompt.
