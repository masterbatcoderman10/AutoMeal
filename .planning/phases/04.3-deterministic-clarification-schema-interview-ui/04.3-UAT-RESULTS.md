### GAP-04.3-P1: Optional Approval Correction Path Is Not Deterministic Enough

Evidence:

- The active state reached `pending_question_ids=["chicken_curry_group:confirm"]` with `remaining_required_question_ids=[]`.
- The bot sent:

```text
I couldn't safely apply that answer yet. Please answer the same meal question again:
I likely have Chicken Curry with Drumstick. Is that right?
```

- `last_turn_error` showed:

```text
ready_to_confirm approved group chicken_curry_group without explicit user confirmation
ready_to_confirm corrected group chicken_curry_group without explicit user evidence
```

Root issue:

- Optional approval prompts (`Yes`/`No`) are being mixed with the resolver confirmation path.
- A `No` answer does not become a deterministic follow-up asking for the corrected food name for that group.
- A typed correction after `No` is treated as a broad confirmation edit, so the validator can still reject it as insufficient explicit evidence.

Acceptance criteria:

- If the user taps `No` on an approval prompt, the next prompt must be a deterministic free-text correction for that same group.
- The typed correction must be stored as the explicit evidence for that group and must not call the LLM resolver just to prove the correction exists.
- After the correction, the flow should proceed to final confirmation/write without re-asking the same Yes/No question.
- Add contract tests covering `No -> typed correction -> final confirmation` for deterministic meal interviews.

### GAP-04.3-P2: Grounding Handoff Blocks Final Writes Too Aggressively

Acceptance criteria:

- User-confirmed meal identity should be written or explicitly held according to a clear policy, not silently stranded in an active interview.
- Add a retry/degraded-state contract test for post-interview grounding failure.

### GAP-04.3-P4: Clarification Contract Should Live Inside Each Food Group

Evidence:

- Langfuse trace `b2199853d60f00172d7be1fbf7c11da0` emitted a top-level `clarification_schema` separate from `food_groups`.
- The top-level schema duplicated group identity fields and required the Telegram/interview mapper to re-join clarification questions back to groups.
- `question_focus` is a model/meta field such as `bread_style`, `vegetable_type`, or `best match`; this leaked into rendered Telegram copy as awkward prompts like:

```text
Which best match best matches the Chicken Drumstick Curry?
Which bread_style best matches the Khubz / Whole Wheat Pita Bread?
```

- The user-facing prompt should be reasoned and emitted directly by the model instead of composed locally from `question_focus`.
- `Other` is currently injected by Telegram after the fact. It should be explicit in the clarification contract so every renderer and validator sees the same allowed answer surface.

Root issue:

- Clarification is modeled as a parallel schema, while the actual reasoning output is already grouped by food.
- This makes the mapper responsible for semantic decisions it should not own: prompt phrasing, choice source, `Other` availability, and how clarification answers attach to food groups.

Acceptance criteria:

- Replace or supersede top-level `clarification_schema` with per-group fields:
  - `clarification_needed: boolean`
  - `clarification_actions: list[object]`
  - `clarification: object | null` only as a deprecated compatibility alias during migration
- `food_group.clarification` must include:
  - `type`, the canonical control field for rendering and answer handling, such as `AFFIRMATION`, `CHOICE`, `SOURCE_ORIGIN`, `QUANTITY`, or `FREE_TEXT`
  - `kind`, optional domain metadata such as `IDENTITY`, `SOURCE_ORIGIN`, `AFFIRMATION`, `QUANTITY`, or `FREE_TEXT`
  - `user_prompt`, written as final human-facing Telegram copy
  - `answer_type`, such as `single_choice`, `confirm`, or `free_text`
  - `choices`, using short user-facing labels
  - `allow_other`, with a defined `other_label`
  - `required`
  - `reason`, explaining why this clarification is needed
  - `validation_hints`
- `clarification.type` must control the option surface:
  - `AFFIRMATION` renders deterministic Yes/No options.
  - `CHOICE` renders the per-candidate choice list plus `Other` when allowed.
  - `SOURCE_ORIGIN` renders the fixed homemade/packaged/restaurant style choices.
  - `FREE_TEXT` renders no inline choices and waits for typed text.
- `clarification_actions` must be an ordered list. Telegram must process the list in order for each food group; for example, `["AFFIRMATION", "SOURCE_ORIGIN"]` means ask affirmation first, then source, without deriving either step from labels or free-form prompt text.
- Each action object must carry all fields needed for rendering and persistence, so Telegram never constructs user-facing copy through string interpolation.
- `question_focus` may remain only as internal trace/debug metadata; it must not be required to render the user prompt.
- Telegram must render `clarification.user_prompt` directly and must not synthesize prompts like `Which {question_focus} best matches...`.
- Compatibility tests should prove the old trace shape can be migrated or rejected clearly during the schema transition.

### GAP-04.3-P5: Use Top-3 Candidates As First-Class Clarification Options

Evidence:

- In trace `b2199853d60f00172d7be1fbf7c11da0`, food groups already contain `top_3` candidate labels with confidence and rationale.
- The separate `clarification_schema.choices` repeated or transformed those candidate labels, creating drift between the model's ranked candidates and the user's visible options.
- The bread group had `top_3` candidates:
  - `Whole Wheat Khubz / Pita pocket`
  - `Thick Brown Pita Bread`
  - `Flatbread (Generic Brown)`
- But the rendered choices became:
  - `Arab Whole Wheat Khubz / Pita Pocket`
  - `Egyptian Baladi Bread`
  - `Thick Roti or Chapati`
  - `Injera style`
  - `Other / Not sure`

Root issue:

- Candidate ranking and user-option generation are split across model output and deterministic mapper logic.
- This allows the user to answer against a choice set that is not the same as the group ranking the model reasoned about.

Acceptance criteria:

- For identity/choice clarifications, `food_group.top_3` should automatically become the primary user choices unless the model explicitly supplies a justified override.
- Identity actions should not carry a separate hand-authored options list by default. Telegram should derive choices directly from `food_group.top_3`.
- Each top-3 candidate must expose:
  - a stable candidate/value field used for persisted answers and downstream resolution
  - a short `quick_prompt` or equivalent display label for Telegram buttons
  - optional descriptor/rationale fields for trace/debug only
- Every identity/choice clarification must include an `Other` / `Not listed` option in the contract, not only in Telegram rendering.
- Choice objects should include stable IDs tied to candidate IDs when possible.
- The mapper must preserve candidate order and must not invent additional food identity options unless a deterministic fallback policy says so.
- Tests should assert that the rendered Telegram choices match the `food_group.top_3` candidate order plus `Other`.

### GAP-04.3-P6: No-Embedding High-Confidence Groups Need Affirmation, Not Silent Auto-Confirm

Evidence:

- The clean-state Langfuse trace emitted the chicken group as:

```json
{
  "group_id": "group_chicken_curry",
  "group_action": "AUTO_CONFIRM",
  "group_state": "READY_TO_WRITE",
  "missing_evidence": []
}
```

- The database had no prior embeddings in the blank-state run, so this was high visual confidence but not learned recognition.
- Local fallback logic later created a deterministic choice/source flow, but that flow was outside the model's food-group contract and contributed to mapper complexity.

Root issue:

- `AUTO_CONFIRM` currently conflates "model is visually confident" with "safe to write learned memory without asking."
- In blank state, high-confidence food identity should still get a lightweight affirmation/source clarification before writing, especially if it will create a new `FoodVisual`.

Acceptance criteria:

- Food groups should distinguish:
  - `AUTO_CONFIRM_LEARNED` for strong embedding-backed matches that can write directly
  - `AFFIRMATION_REQUIRED` for high visual confidence without learned embedding support
  - `IDENTITY_CLARIFICATION_REQUIRED` for ambiguous identity
- For high-confidence no-embedding groups, emit `clarification.kind = AFFIRMATION` with a human prompt such as `I think this is chicken drumstick curry. Is that right?`
- For high-confidence no-embedding groups, emit `clarification.type = AFFIRMATION`; Telegram must derive the Yes/No buttons from that type.
- Affirmation clarifications must always map to deterministic Yes/No answer handling.
- A `No` answer must deterministically ask for the corrected food name for the same group.
- Source-origin clarification should be represented as a `SOURCE_ORIGIN` action in the same group's `clarification_actions` list when needed for grounding/nutrition, not as a separate mapper-invented question.

### GAP-04.3-P7: Expand Reasoning Payload Before Telegram Mapping

Evidence:

- The current mapper compensates for missing reasoning details by constructing prompts, adding `Other`, deriving source questions, and deciding when to ask affirmation.
- This caused UI copy defects, ordering bugs, and finalization ambiguity in live Telegram UAT.

Root issue:

- The reasoning model is not being asked to produce a complete interaction contract.
- Telegram is doing semantic orchestration instead of only rendering model-owned clarification intent and recording answers.

Acceptance criteria:

- The reasoning prompt/schema should require the model to think through, per food group:
  - identification certainty
  - embedding/memory support versus visual-only confidence
  - whether source/homemade/packaged/restaurant grounding matters before saving
  - whether affirmation, identity choice, source-origin, quantity, or free-text clarification is required
  - the ordered `clarification_actions` list needed for that food group
  - a final human-friendly prompt and answer surface
- Telegram should become a renderer/transport layer for the per-group contract: iterate `food_group.clarification_actions`, render by `action.type`, persist structured answers, and never infer semantic steps from display strings.
- Validation should reject food groups where `clarification_needed=true` but `clarification.user_prompt` or valid choices are missing.
- Langfuse trace review should show the full clarification contract under each `food_group` before any Telegram-specific transformation.
