## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Telegram reply metadata -> interview session resolver | Chat text and reply metadata decide which meal state is mutated and therefore must be resolved deterministically or rejected as ambiguous. |
| meal interview routing -> `/fix` routing | The new meal-session LLM path must not capture or corrupt deterministic correction sessions. |
| live Telegram/Langfuse verification -> planning evidence | Manual validation must prove routing safety and trace completeness against the shipped code paths, not against a synthetic shortcut. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04.2-09 | Spoofing | `bot/handlers.py` | mitigate | Resolve meal-session replies by `reply_to_message.message_id` -> `InterviewSession.last_bot_message_id` first, then allow newest-session fallback only when exactly one active session exists. |
| T-04.2-10 | Tampering | `bot/handlers.py` / `app/services/interview_service.py` | mitigate | Fail closed with an explicit retry instruction when multiple active sessions exist and the reply does not identify one prompt; do not guess which meal owns the reply. |
| T-04.2-11 | Elevation of Privilege | `/fix` correction flow | mitigate | Keep `SESSION_MODE_FIX` on the deterministic correction path and regression-test that `USER_CORRECTED` still flows through `apply_confirmed_entry_correction()` and the existing invalidation logic. |
| T-04.2-12 | Repudiation | live UAT evidence | mitigate | Add `04.2-UAT.md` with concrete Telegram and Langfuse checks for bottle-gourd composition, simultaneous active meals, and traced structured responses. |
| T-04.2-SC | Tampering | package-manager surface | accept | No new packages or install tasks are allowed in this phase; routing hardening must use existing models, tables, and bot surfaces only. |
</threat_model>
