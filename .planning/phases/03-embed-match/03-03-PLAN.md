## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| similarity decision -> diary persistence | Business-rule decisions become durable nutrition history and must not partially commit. |
| confirmed match -> `FoodVisual` append | New training examples enter the visual corpus and must only be written for fully confirmed meals. |
| committed DB rows -> later Telegram push | Persistence must succeed independently of bot delivery so notifications cannot roll back user data. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-09 | Tampering | `app/services/matching_service.py` | mitigate | Write `DiaryEntry`, `FoodVisual`, and `MealLog.processing_status=COMPLETED` inside one transaction per D-24. |
| T-03-10 | Integrity | `app/services/matching_service.py` | mitigate | Apply D-13 and D-15 by forcing `portion_bucket=STANDARD` and copying only existing `FoodItem` nutrition fields without scaling or fabrication. |
| T-03-11 | Tampering | `app/models/food_visual.py` writes | mitigate | Suppress write-back when any segment is unresolved per D-23 and append duplicate confirmations intentionally per D-22. |
| T-03-12 | Denial of Service | `bot/polling.py` | mitigate | Keep notification out of the transaction per D-25 so a send failure cannot hold locks or undo committed meal rows. |
| T-03-SC | Tampering | Python dependency/runtime surface | accept | No new packages are installed in this plan; rely on the existing locked stack from Phase 1. |
</threat_model>
