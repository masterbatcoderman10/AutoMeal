### Locked Decisions

- **D-01:** If a food group has no vector match or fewer than 5 vector matches, the deterministic clarification flow must ask a source question even if reasoning did not explicitly request one.
- **D-02:** For ambiguous learned distributions, resolve identity first, then decide whether source still needs to be asked.
- **D-03:** Existing clarification ordering, answer persistence, partial-reply recovery, and rerender behavior must remain intact.
- **D-04:** `PACKAGED_BRANDED` and `STORE_BOUGHT_PREPARED` remain distinct downstream states.
- **D-05:** Store-bought retail can still ask for brand; restaurant can still ask for restaurant name.
- **D-06:** Source, brand, and restaurant answers remain pre-finalizer inputs, not a new write/finalization subsystem.
- **D-07:** Strong learned history does not remove identity choice when identity is still ambiguous.
- **D-08:** After identity selection, a strong learned source distribution should produce an affirmation prompt instead of the generic source question.
- **D-09:** If learned source consensus is not strong enough for the selected identity, fall back to the generic source question.
- **D-10:** The dominance threshold is planner discretion, but must be meaningfully strong before using affirmation.
- **D-11:** Rejecting an affirmation must lead to a free-text correction prompt.
- **D-12:** The correction answer is the authoritative answer forwarded downstream.
- **D-13:** The existing failed-affirmation correction path should be reused for source affirmations too.
- **D-14:** Group contracts must expose stable `segment_ids: string[]`.
- **D-15:** Phase 04.5 stays inside interview/Telegram scope. No grounding loop, no finalizer redesign, no whole-meal interview regression.

- Exact rendering of the source-consensus affirmation, as long as it remains deterministic.
- Whether brand/restaurant follow-ups are injected immediately after source or through the existing dynamic insertion path.

## Summary

The codebase already has the right primitives for 04.5. `reasoning_service.py` can synthesize clarification actions when model output is incomplete, `interview_service.py` already owns deterministic ordered question state plus dynamic follow-up insertion, and rejected affirmations already become same-group free-text corrections. The gap is not infrastructure; it is decision logic. Today source questions are mostly emitted from `_needs_source_origin_question()` or model-authored actions, and they are not yet driven by vector-match count or post-identity learned-source consensus.

The lowest-risk design is:

1. Add source-trigger metadata and consensus hints in `reasoning_service.py` when normalizing each food group.
2. Keep identity-first ordering for ambiguous groups by injecting source only after identity choice has been resolved in state.
3. Represent learned-source affirmations as the same deterministic question shape already used for approval/affirmation prompts.
4. Reuse `_build_affirmation_correction_question()` for rejected source affirmations so the recovery path is identical to the existing one.
5. Preserve `confirmation_items` as the only grouped handoff into Phase 04.4 finalization.

**Primary recommendation:** Implement the learned-source branch as metadata plus dynamic question insertion in `interview_service.py`, not as a new branch in bot handlers. Bot handlers should stay dumb: render the next prompt, persist the answer, rerender the next prompt.

## Architecture Patterns

### Pattern 1: Gate-Side Trigger Synthesis Before UI

**What:** Keep source-trigger heuristics in `reasoning_service.py`, next to `_evaluate_group_gate()` and `_build_group_clarification_actions()`.

**Why:** The reasoning layer already decides whether a group is auto-confirmable, affirmation-only, or identity-clarification-required. Source-trigger rules derived from vector counts and learned history belong beside that decision, not in Telegram handlers.

**Recommended implementation shape:**

- Extend normalized group payloads with metadata such as:
  - `match_count`
  - `selected_identity_food_item_id`
  - `learned_source_distribution`
  - `source_question_policy` (`ask_generic`, `ask_affirmation`, `skip_until_identity`)
  - `source_trigger_reason`
- Keep `clarification_actions` compact and deterministic. Do not encode branching prose into handlers.

**Code seams:**

- `_evaluate_group_gate()`
- `_build_group_clarification_actions()`
- `_existing_actions_for_group_action()`
- `_clarification_actions_for_group_action()`

### Pattern 2: Identity-First, Source-Second Dynamic Injection

**What:** For groups where identity is still unresolved, do not pre-ask source affirmation for a specific learned identity. Instead, ask identity first, then inject the source question or source affirmation after the identity answer is known.

**Why:** This matches D-02 and avoids showing a source consensus for the wrong identity candidate.

**Recommended implementation shape:**

- After an identity answer is recorded in `_apply_clarification_answer()`, inspect the chosen identity and its attached source consensus metadata.
- Insert one of:
  - generic `SOURCE_ORIGIN`
  - learned-source `AFFIRMATION`
  - no source question at all
- Insert the new question immediately after the identity question and before later unrelated prompts, preserving ordered deterministic flow.

**Code seams:**

- `_apply_clarification_answer()`
- `_answer_record_for_question()`
- `_confirmation_items_from_clarification_answers()`

### Pattern 3: Reuse Affirmation Rejection As-Is

**What:** Model learned-source confirmation as a normal affirmation prompt, then let `_build_affirmation_correction_question()` handle rejection.

**Why:** The current code already transforms rejected affirmations into a required same-group free-text correction prompt. That is exactly the user’s desired behavior for source affirmation failure.

**Implication:** No new “source-rejection” state machine is needed. The only real change is what label/prompt the affirmation uses and how the final free-text answer is interpreted downstream.

### Pattern 4: Follow-Up Source Detail Questions Stay In The Same State Machine

**What:** Brand and restaurant follow-ups should be represented as normal deterministic questions in `questions_by_id`, not as special-case ad hoc prompts.

**Why:** Required-question recovery, stale callback protection, and replay persistence already assume that every pending prompt is in the same question inventory.

**Recommended follow-up types:**

- `SOURCE_ORIGIN` -> `PACKAGED_BRANDED` or `STORE_BOUGHT_PREPARED`
  - optionally inject free-text `brand_name`
- `SOURCE_ORIGIN` -> `RESTAURANT`
  - inject free-text `restaurant_name`

**Constraint:** Keep these questions group-scoped with the same `segment_ids`.

### Pattern 5: Preserve 04.4 Handoff Boundaries

**What:** `confirmation_items_from_state()` remains the only place that composes grouped user answers into finalizer input.

**Why:** Phase 04.4 already expects grouped `segment_ids`, source fields, and names. 04.5 should enrich those payloads, not create a second post-processing stage.

**Recommendation:** Keep any new fields additive and compact. Examples:

- `source_origin_state`
- `brand_name`
- `restaurant_name`
- `identity_choice_source` (`learned`, `manual`, `affirmed`)
- `source_choice_source` (`generic_question`, `learned_affirmation`, `free_text_correction`)

## Recommended Heuristic Shape

Use a conservative two-step source policy:

1. **Pre-identity source trigger**
   - Ask generic source if there are no usable matches or fewer than 5 matches.
   - Do not ask learned-source affirmation before identity is explicit.

2. **Post-identity source policy**
   - If the selected identity has a strong learned source distribution, ask affirmation.
   - Otherwise ask generic source.

Reasonable planner-ready dominance heuristic:

- minimum supporting learned matches for the selected identity: `>= 5`
- dominant source share: `>= 0.8`
- dominance gap over the next source bucket: `>= 0.4`

This is intentionally conservative. It will avoid over-triggering affirmations when history is noisy.

## Common Pitfalls

### Pitfall 1: Asking Source Affirmation Before Identity Choice

This creates wrong or confusing prompts when multiple candidate identities have different learned source histories.

### Pitfall 2: Injecting Questions In Bot Handlers Instead Of Interview State

That would bypass `pending_question_ids`, replay persistence, and required-first ordering.

### Pitfall 3: Treating Rejected Source Affirmation As Another Fixed-Choice Ladder

That would regress the current correction flow and violate D-11/D-12.

### Pitfall 4: Dropping `segment_ids` Or Group Scope On Follow-Ups

Brand/restaurant/source corrections must stay attached to the same food group or Phase 04.4 finalization will lose provenance.

### Pitfall 5: Letting `Other` Leak Into `SOURCE_ORIGIN`

`bot/callback_data.py` intentionally disables `Other` for `SOURCE_ORIGIN`. Keep that rule unless the entire parsing contract is redesigned.

### Pitfall 6: Reordering Optional/Required Questions Incorrectly

Source or brand follow-ups inserted at the wrong position can make the bot loop or re-ask already-satisfied prompts.
